# Recovery gateway — 2026-09-07

The gateway implements the six fixed release-auth endpoints. It rejects any
Origin, wrong scheme/host/path/method, query/fragment, invalid media/encoding,
duplicate/extra JSON fields, invalid UTF-8, declared/streamed overflow and
length mismatch. GET endpoints accept no body. Success returns one opaque JWS
field; failure returns only fixed code and validated request UUID or null.
All responses are JSON/no-store with no CORS or redirect headers.

Request reads have a 32 KiB cap and a 10-second overall body deadline. RPC waits
are bounded at 390 seconds for issue, 95 for claim and 20 for other methods,
within the existing client timeouts. An RPC timeout does not prove cancellation
or failure of a durable operation; the gateway never retries automatically.
Safe log events have exactly the six specified fields and cannot contain raw
tokens, JWS, URLs, arbitrary errors or provider metadata. Logger failure cannot
replace a successful operation response. Worker observability remains disabled.

## Runtime-driven compatibility corrections

The first actual named-Worker-RPC test found two differences from in-memory
mocks:

1. Workerd adds a nonenumerable `Symbol.dispose` function to returned objects.
   Gateway-only response handling recognizes that exact lifecycle descriptor,
   disposes the result, and applies the unchanged exact-data validator to the
   remaining fields. Other symbols, enumerable lifecycle fields, accessors and
   extra data still fail. This exception is never used for HTTP request data.
2. Workerd rejects null-prototype request objects with DataCloneError. After
   validation, the gateway copies only the approved string fields into a normal
   object for RPC transport. It never spreads unvalidated request data.

These bounded compatibility corrections are based on observed runtime failures,
not a relaxation of authentication or the public endpoint contracts.

# Warpkeep 0.4 isolated gameplay successor

Status: design for implementation under the owner's standing authorization;
not evidence of implemented or deployed gameplay. G002 admissions alone remain
TBD by explicit user instruction and stay closed.

## Scope and architecture

Ship the existing gather → choose → build → benefit loop using a shared pure
0.4 policy/state-transition core and distinct PTR/G002 database adapters.
Import no live G001 schema, Worker authority, or Inner Keep authority into the
new core. Leave every frozen G001 source projection and persistent row intact.
Directly reusing G001 authorities would import fixed G001 identities and site
catalogs; duplicating two complete gameplay implementations would create drift.
The shared core with thin realm adapters is the selected approach.

PTR commands require the existing authenticated owner boundary on every
transaction: current issuer/audience/expiry, signed database identity, unique
enabled owner anchor and matching FID/auth epoch. Atlas-admin credentials are
not player authority. No request supplies the acting FID or authoritative keep.
G002 deploys the same mechanics and private schema but its player command gate
always rejects while closed; neither an admin role nor deployment opens play.
This is an explicit closed release mode, not an unavailable implementation stub.

## Persistent state and atomic commands

Use new private 0.4-owned tables for keep/account, four Workers, buildings,
one active construction project, and bounded command receipts. Do not populate
legacy resourceAccount/worker/castle/player/admission descriptors: current PTR
connection, status, suspension and atlas checks intentionally require them empty.
Keep that invariant and update exact schema/source closure tests deliberately.

Initialize the owner keep once in an authenticated transaction, with zero
resources, four idle Workers and no buildings. Bind it to the actual database,
owner FID, policy version, atlas ID/import revision and validated existing PTR
component-zero root view anchor. Re-entry never reseeds or overwrites it. A
changed atlas binding fails closed for explicit migration, never automatic reset.
The existing public view's castle ID equals owner FID; preserve that projection
without inserting a legacy castle row. Never expose private FID through new
public gameplay tables.

Commands are initialize, read/reconcile state, dispatch Worker, recall Worker,
and start/upgrade building. Every mutation uses a bounded request key and exact
expected aggregate revision. Store the accepted canonical input fingerprint and
result; same key/same payload replays without additional effect, different payload
rejects. Reauthenticate before any replay. Retain the latest 128 receipts with
monotonic command sequence; older sequence numbers reject and never become fresh
after pruning. Reject overflow rather than wrapping. Policy and layout digests
bind construction quotes. Validate all inputs before writing; reconciliation,
resource settlement, deductions, project and receipt commit atomically.

Use integer microsecond server timestamps and checked integer resource arithmetic.
Balances cap at 1,000,000 per resource. Settlements credit at most remaining
capacity and report capped overflow explicitly. No browser clock, client balance,
client route, client yield or predicted completion is authority.

## Workers and progression

Keep four independent Workers and the existing outbound/gathering/returning/idle
model. Dispatch resolves a real resource location, resource kind and valid route
from the isolated verified atlas. Use its node capacity; reserve one node per
active expedition until return, transactionally. Reject nonexistent, unreachable,
wrong-revision, full or wrong-kind targets. Preserve a bounded private route
commitment and expose only validated public route coordinates for animation.

0.4 travel takes two seconds per validated route edge. Gathering uses ten-second
quanta, base yield ten units per completed quantum for each resource kind, with
available duration choices 60 seconds, 10 minutes, 1 hour and 8 hours. Resolve
yield effects at dispatch and persist that rate; later upgrades do not rewrite
an expedition already underway. Return travel uses the validated outbound route
in reverse. Recall starts return from the authoritative current route position
or gathering site; never teleport, double-credit or accrue after departure.
Resources become spendable on return, not from an optimistic client estimate.

Authoritative reconciliation derives elapsed phases from persisted timestamps,
so disconnect/background/offline time neither pauses nor duplicates work. A
server scheduler handles due transitions; reads/commands can reconcile overdue
canonical state transactionally if delivery was delayed. Suspension rejects
commands without deleting state; reauthorization resumes reconciliation.

## Construction policy

Keep six existing building kinds, five levels, one Builder, permanent placement,
no queue, cancellation, relocation, refund, payment, combat or new resource kind.
Reuse existing presentation assets and continuous interior placement semantics
(half-meter grid, quarter turns, support boundary, civic/road exclusions and
oriented collision checks) through isolated 0.4 policy, not G001 authority.
Upgrade retains the exact persisted transform.

Level-one costs in food/wood/stone/gold are: Mill 20/40/20/0; Lumber Camp
20/20/40/0; Stoneworks 40/20/20/0; Goldworks 40/60/40/20; Barracks
60/80/80/40; Cathedral 80/100/120/60. Target-level cost multipliers are
1, 3, 7, 15, 31 with exact integer multiplication and no hidden discounts.
Target-level build durations are 2 minutes, 15 minutes, 1 hour, 4 hours,
and 12 hours. Maximum level is five.

Completed Mill/Lumber Camp/Stoneworks/Goldworks levels each add 20% of base
gathering yield to their matching resource, capped at +100%. Barracks reduces
travel time by 5% per completed level (maximum 25%, integer microseconds rounded
up). Cathedral reduces future construction duration by 5% per completed level
(maximum 25%, rounded up); it does not alter an already accepted project.
Effects require completed levels and are captured in the next command's quote.
These benefits improve the existing loop without introducing military or faith
systems. G001 recipes, discounts and timings are unchanged.

## Client integration and acceptance

Provide a narrow realm-bound gameplay client, distinct from G001 provider state.
Clear it on realm/session/database/epoch changes and discard stale async replies.
Display authoritative balances, four Worker phases/routes, exact costs, travel,
build countdowns and before/after benefits. Show permanent-placement warnings
before confirmation, pending/retry states without optimistic resource spending,
and a visible next action. Reuse the actual voxel realm scene and Inner Keep
presentation; synthetic QA alone cannot satisfy this integration.

Verify deterministic core transitions, duplicate/conflicting/reordered commands,
overflow, invalid state, exact timer boundaries, capacity, collision, stale quotes,
authorization expiry/rotation/suspension and cross-database rejection. Compile
both modules, generate actual bindings with the local pipeline, prove private
schema and exact source closure, and test G002's closed denial with zero writes.
Run the real owner PTR journey: initialize, gather, return, build, completion,
observe improved next expedition, disconnect/reconnect and realm switch. Measure
first payoff on actual atlas routes: a first economy building and its improved
return must be achievable within ten minutes of active play using nearby valid
resources. If actual topology fails this gate, adjust the 0.4 route/starting-anchor
design explicitly; do not invent resource sites or waive the journey test.

This spec does not finish local release tooling, production verification, PR
reconciliation or Desktop handoff; those remain requirements of the full goal.

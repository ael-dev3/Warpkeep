# Warpkeep 0.4.0 sealed-realms release design

Status: owner approved on 2026-08-30

## Outcome

Warpkeep 0.4.0 ships a production launcher with three independently secured
realm choices:

| Realm | Version | Player access | New admissions | Purpose |
| --- | --- | --- | --- | --- |
| Genesis 001 | exact `0.3.43` forever | existing admitted players only | permanently closed | preserved live game |
| Genesis 002 | `0.4.0` | nobody | closed until a separately approved release | sealed Greater Realm |
| Public Test Realm (PTR) | `0.4.0-ptr.1` | one configured owner-admin only | no public admission surface | isolated testing of future patches |

The client exposes all three choices in a dedicated selector within the
`ENTER REALM` screen. Genesis 001 remains the default. A realm may be selected
for inspection even when entry is unavailable, but selection alone never
authenticates, admits, connects, or mutates backend state.

This design supersedes the two-choice outcome in
`2026-08-27-realm-chooser.md` and the earlier Greater Realm cutover plan. It
retains the sealed Genesis 002 design and extends it with a separate PTR and a
permanent Genesis 001 preservation boundary.

## Realm isolation

Each realm has a distinct full SpacetimeDB identity. Aliases are permitted only
as one-time publication inputs and human labels; clients, receipts, imports,
and production verification bind full lowercase 64-hex identities. Genesis
identities and the PTR identity must be pairwise distinct.

Genesis 001 keeps its existing database, data, player set, gameplay schema,
and `0.3.43` player-facing version. Genesis 002 and PTR are fresh databases
published from separate modules. No migration, table copy, database rename, or
republish may cross the three security domains.

### Genesis 001 preservation

Genesis 001 remains playable for identities already admitted at the freeze
boundary. All request, allow, admit, founder, disable, revoke, reset, auth-epoch,
relocation, deactivation, and re-enable writers fail before database or audit
effects. Legacy Greater Realm relocation and deactivation code must be removed
from the active release authority or guarded by a permanent refusal that is
covered by tests and release verification.

The exact live policy is:

- realm version `0.3.43`;
- existing-player access enabled;
- new admission and access requests disabled;
- the admitted set preserved;
- no realm relocation or deactivation;
- no future source publication to the Genesis 001 database.

Read-only status and observation remain available through the protected
administrator path. Public admission requests stay suspended at the auth
bridge before authentication, rate limiting, database access, or notification
delivery.

### Genesis 002 sealed realm

Genesis 002 uses the private `spacetimedb/genesis002` module and release
`0.4.0`. It contains the finalized selected Greater Realm atlas but has zero
players, admissions, founders, castles, claims, occupancy, activation rows,
Worker rows, and public tables. It exposes no player authentication, request,
admission, subscription, or entry route.

Only the bounded administrator atlas-import surface exists during launch.
Every writer proves zero population both before and after its effect and becomes
permanently inert after finalization. Future admission, activation, player
presentation, or founding requires a separate reviewed design and release.

### Public Test Realm

PTR uses the private `spacetimedb/ptr` module, alias `warpkeep-ptr`, module
identity `warpkeep-ptr-owner-view-v1`, atlas `PTR_GREATER_REALM`, and release
`0.4.0-ptr.1`.

PTR has no public admission or access-request surface. Its only player anchor is
the singleton owner FID supplied through the protected
`WARPKEEP_PLAYER_CANARY_OWNER_FID` secret. Entry requires a short-lived,
server-bound token with all of the following exact claims:

- PTR database identity;
- PTR realm and role;
- distinct PTR OIDC audience;
- configured owner FID;
- maximum lifetime of 120 seconds.

The Hermes administrator remains an operations principal, not a second player.
Any missing, additional, disabled, or mismatched owner anchor fails closed.
Later test players require a new reviewed access model.

## Client interaction

The `ENTER REALM` screen presents one keyboard-accessible, screen-reader named
selector containing `Genesis 001`, `Genesis 002`, and `Public Test Realm`.
Every choice has a text status and an icon/tooltip so color is never the only
signal.

- Genesis 001 shows available only for a currently authenticated, already
  admitted player. Entry reuses the existing `0.3.43` path.
- Genesis 002 always shows sealed. Entry performs no network or authentication
  action and displays the deterministic suspension notice.
- PTR shows available only after server-verified owner authority. Non-owner,
  anonymous, expired, checking, and error states remain locked and perform no
  database connection.

Realm selection is presentation state only. It is not stored in local storage,
query parameters, cookies, or any authority-bearing persistence.

## Auth bridge and Cloudflare boundary

The production Worker keeps public admission requests suspended for both
`POST` and CORS `OPTIONS` on `/v2/access/request`, returning exact HTTP 503 and
`admission_requests_suspended` before any downstream work.

PTR token minting is a separate fail-closed route and audience. Worker versions
are uploaded using predecessor-bound `keep_bindings` semantics and verified
against the exact predecessor and latest uploaded version. An ambiguous upload
or receipt state stops the release; it never authorizes a retry or activation.
Secrets, FIDs, private receipt bodies, and raw tokens must not enter repository
files, Pages variables, Actions logs, or public release bindings.

G002 and PTR publication authority is independent of the auth bridge. Each
publisher uses only the pinned authenticated SpacetimeDB 2.6.1 CLI and follows
submission with an authenticated, read-only CLI identity/list postflight. A
publish inspection may adopt a possibly submitted publication only when it
reconciles the exact fresh identity; otherwise it must prove the alias absent
before issuing a new one-time confirmation. It never retries a possibly
submitted publication.

Both publisher/CLI pairs expose the same pure canonical ambiguity value before
submission: profile
`warpkeep-sealed-realms-publication-possibly-submitted-v1`, with exact ordered
fields `schemaVersion`, `profile`, `lane`, `sourceCommit`, `databaseUri`,
`alias`, `moduleIdentity`, `release`, `artifactDigest`, `toolchainDigest`,
`publishPlanDigest`, `confirmationDigest`, `attemptNonce`, `markedAt`, and fixed
`submissionState=possibly-submitted`. It is bounded canonical UTF-8 JSON,
contains no database identity or private field, and is never a confirmation,
receipt, adoption decision, or activation input. Task 6C exports pure canonical
constructor/parser/digest and marker-to-receipt reconciliation constructor
ABIs. The publish inspect binds the exact publish plan plus its confirmation,
persists the marker bytes no-clobber, and fsyncs before returning that
confirmation or permitting apply. Apply reopens it before releasing the CLI
callback. A crash or
ambiguous return therefore blocks another confirmation until the existing
publish inspect authenticates CLI state and appends exact adoption or alias-
absent/no-effect reconciliation; the submitted publication is never replayed.

The protected prepared-bridge workflow remains the sole deploy/recovery
authority. Its content-addressed prepared receipt lives below
`~/.warpkeep/private/production-admin-v1/bridge-prepared-receipts-v1/` as
`auth-bridge-notification-prepared-<receiptDigest>.json`. No workflow input,
caller-selected path, or caller-selected digest may identify that receipt.
The dispatcher deterministically requires exactly one eligible receipt and
authenticates only its canonical body/digest, source `S`, prepared/expiry
times, and expiry. A strictly read-only scan of the existing completed journal
below
`~/.warpkeep/private/production-admin-v1/bridge-prepared-deploy-journal-v3/`
independently derives the unique successful run/attempt and completed deploy-
or-recovery outcome. Fresh private/public deployment attestation derives the
deployment ID, latest Worker version, and source commit; fresh credentialed
private attestation derives the PTR identity/binding and attestation digests.
Those facts form one immutable `deploymentAuthority` record and never come
from the prepared receipt or caller.

Bridge authority state lives only below
`~/Library/Application Support/Warpkeep/operations/runtime/sealed-realms-v1/bridge/`
in bounded, no-clobber, owner-only append-only files. Its exact physical grammar
is one `deploymentAuthority`, zero-or-more abandoned `g002Gate` records, one
final consumed `g002Gate`, exactly one `g002ImportAuthorityCrossLink`, zero-or-
more abandoned `ptrGate` records, one final consumed `ptrGate`, then exactly one
`ptrImportAuthorityCrossLink`. Each new gate names exactly its immediately
superseded same-lane predecessor; the old gate is never modified. An earlier
gate is unusable because the next gate names it, and only the final gate may be
named by its lane cross-link. Forks, cycles, skipped predecessors, or any gate
after its lane cross-link fail closed.
`g002-import-inspect` reopens `deploymentAuthority`, freshly reattests the
unchanged deployment and PTR binding, performs both authoritative POST and
OPTIONS probes, and appends a lane-specific `g002Gate`; its confirmation binds
that gate. G002 apply consumes it and appends
`g002ImportAuthorityCrossLink` to the unchanged immutable G002 import-receipt
digest. After G002 import, `ptr-import-inspect` independently reopens the same
authority, freshly reattests deployment/binding, performs both probes, and
appends `ptrGate`; PTR apply consumes its own gate-bound confirmation and
appends `ptrImportAuthorityCrossLink` to the unchanged immutable PTR receipt.
Each consumed gate must be no more than five minutes old at its own apply, and
both gates must bind the same deployment authority, version/source, PTR
identity, and binding. A gate atomically binds one fresh deployment attestation,
one fresh binding attestation, and both fresh probes; mixing a refreshed
component with any prior observation is invalid.

An expired unused or ambiguous confirmation is permanently unusable. The same
existing inspect operation may append a same-lane superseding gate only after
read-only reconciliation proves no effect; if an exact submitted realm import
is adopted, it appends the exact receipt cross-link without replaying the
mutation. Superseded same-lane gate revisions remain immutable within their
lane segment; the final consumed chain obeys the exact physical grammar above.
No record is overwritten,
replaced, reordered, skipped, or silently refreshed. Once a lane cross-link is
sealed, that lane can only be read/adopted and never receives a new mutation
gate.

No new gate may be appended after the prepared receipt expires. A completed
realm receipt can still be authenticated for exact adoption, but it cannot by
itself authorize a missing later lane. The sole recovery is the protected
prepared workflow's internal `recover-expired-authority-read-only` action and
entrypoint `runAuthBridgeNotificationPreparedReadOnlyRecovery`, with exact
outcome `verified-read-only-recovery`; it is not a dispatcher operation. It
does not reuse the current top-level prepared receipt writer, because that path
always invokes its deploy callback. New Cloudflare-runtime read API
`inspectAuthBridgeNotificationPreparedRecoveryAuthority` performs deployment
and deployable/latest-upload enumeration, inspects the exact old completed-head
version, requires it to remain the unique latest deployed version, and performs
fresh pre/post public, credentialed private, control-plane, and PTR-binding
attestations. It may reuse pure adapter attestation helpers but never calls the
deploy adapter executor; read-only reconciliation/inspection may run while
upload/release/deploy callbacks are absent or fail-if-called. It requires the expired chain's unchanged deployment ID,
latest Worker version/source commit, PTR identity, and binding.

The recovery writes one new content-addressed prepared receipt with fresh
prepared/expiry times and one append-only completed recovery journal/head. The
head binds outcome `verified-read-only-recovery`, the new receipt digest, old
expired receipt/head digests, protected run/attempt, unchanged deployment/
version/source and PTR identity/binding, fresh control-plane/public/private/
binding attestation digests, completion time, and an exact no-deploy assertion.
The head profile is exactly
`warpkeep-auth-bridge-notification-prepared-read-only-recovery-v1`; its ordered
canonical schema is `schemaVersion`, `profile`, `sourceCommit`, `runId`,
`runAttempt`, `priorPreparedReceiptDigest`,
`priorCompletedJournalHeadDigest`, `preparedReceiptDigest`, `deploymentId`,
`workerVersionId`, `bridgeSourceCommit`, `ptrDatabaseIdentity`,
`ptrBindingDigest`, `controlPlaneAttestationDigest`,
`publicAttestationDigest`, `privateAttestationDigest`,
`ptrBindingAttestationDigest`, `completedAt`, `noDeploy`, and `outcome`, with
fixed version `1`, `noDeploy=true`, and the named outcome.
The new physical authority path is derived without caller input as
`auth-bridge-import-authority-<authorityChainDigest>.jsonl`, where the digest
commits to profile, `S`, new receipt/head digests, deployment ID/version, and
PTR-binding digest. The old receipt, journal, gates, and authority file remain
byte-identical and terminal; orphan or duplicate eligible pairs, two completed
heads, drift, revival, overwrite, or mutation fail closed.

On this new chain, the existing G002 inspect operation freshly gates the
already-completed immutable G002 receipt. The existing `g002-import-apply` name
selects a new dispatcher adoption branch that authenticates the durable receipt,
freshly verifies inspect/live state, and appends only its cross-link; it never
calls the G002 import core or reducer. The `ptr-import-apply` name uses the same
dispatcher-only branch for a completed PTR receipt because its current import
core rejects already-applied state. If PTR is missing, exact no-effect proof
permits one ordinary PTR core/reducer call under its new gate. Only after the earlier completed lane
is re-adopted may the missing lane proceed. `activation-evidence-inspect`
validates both lane gates and
cross-links share the same current authority/source/PTR binding, refreshes
deployment and binding attestations, and performs fresh POST and OPTIONS probes.
Its observation must be no more than five minutes old when generation starts.
Zero/multiple eligible receipts, incomplete/ambiguous journal, failed/stale run
attempt, abandoned-confirmation revival, partial refresh, wrong predecessor or
order, cross-lane gate substitution, missing/wrong cross-link, one-probe-only
success, replay, redeploy/binding drift, or ambiguous result blocks release.
Only the protected bridge workflow reconciles deployment ambiguity; it is not a
new sealed-realms operation.

The exact dedicated private envelope member is
`authBridgeSuspensionPrivateReceipt`, profile
`warpkeep-sealed-realms-auth-bridge-suspension-private-v1`. Its authenticated
body binds the prepared receipt/source/expiry, unique completed journal/outcome/
run/attempt, deployment ID/latest Worker version/source commit, PTR identity/
binding and attestation digests, both independent lane gates and immutable
realm-receipt cross-links, fresh activation POST/OPTIONS evidence, timestamps,
distinct nonces, predecessor digests, and all chronology/freshness links.
Its exact ordered top-level schema is `schemaVersion`, `profile`,
`sourceCommit`, `deploymentAuthority`, `g002Gate`,
`g002ImportAuthorityCrossLink`, `ptrGate`,
`ptrImportAuthorityCrossLink`, and `activationGate`.
The envelope embeds only each lane's final consumed gate and its cross-link;
terminal superseded revisions remain authenticated private dispatcher history.
`deploymentAuthority` contains canonical prepared receipt body/digest/times,
journal head/run/attempt/outcome/completion/predecessor, deployment ID/version/
source, PTR identity/binding, and initial attestation digests. Each lane gate
contains its authority/predecessor and single nullable `supersedesGateDigest`,
observation timestamp, nonce, fresh deployment/binding attestation digests, and
exact POST/OPTIONS evidence. Each cross-link contains authority, predecessor,
consumed-gate, immutable realm-receipt digest, adoption/apply outcome, and
timestamp. `activationGate` contains both lane/cross-link digests, its fresh
attestation/probe evidence, timestamp, and distinct nonce. Every object is
canonical, bounded, ordered, and rejects extra or missing keys.
Raw bodies and the private receipt never leave private state. The generator
requires the candidate `authBridgeSourceCommit` and
`admissionRequestSuspensionReceiptDigest` to be exactly null, rejects every
caller-provided bridge field, and deterministically derives the public
`authBridgeSourceCommit`, `admissionRequestSuspensionReceiptDigest`, and its
existing opaque commitment from this member. This adds no new public
commitment.

PTR has three disjoint mutation-authority lanes and receipts: publication,
ownerless atlas import, and configured-owner provision. Publication creates
only the fresh database. Ownerless atlas inspection/import authenticates the
publication receipt, carries no owner FID, auth epoch, entropy, proof, or
owner-bearing token, and proves zero owner state before and after finalization.
Configured-owner inspection reopens the exact atlas-import receipt, and only
configured-owner provisioning may resolve the live G001 owner, obtain the
fresh owner-bearing Task 4 token, derive the private opaque owner proof, and
write the provision receipt. A distinct read-only live receipt cross-links the
provision proof after mutation; it is not a fourth mutation-authority lane.
Publication/import receipts and output contain no owner FID or auth epoch.

## Genesis 001 evidence boundary

mandatory two-pass evidence pairs. The applicant archive proves the bounded
access-request population and retains its separately private human-readable
export. The admitted-player census is a new read-only lane outside
`GENESIS_001_ADOPTION_SOURCE_PROJECTION_PATHS`; it proves the complete enabled
`allowed_fid` set and stable auth epochs. Neither proof substitutes for the
other.

The preferred pinned query is exactly
`SELECT fid, enabled, auth_epoch FROM allowed_fid`. It is bounded and

`enabledAllowedFids` before and after the read. If that query shape is not
available without changing the frozen ABI, the sole fallback enumerates
`player_v2`, checks each FID with the existing administrator status procedure,
and requires the reconstructed enabled set to equal aggregate `allowedFids`.
Any partial, changing, populated-with-disabled-rows, or aggregate-mismatched
result blocks release.

`g001-census-first` collects pass one of both evidence pairs.
`g001-census-second-inspect` collects pass two of both, requires private
stability across distinct nonces and timestamps within 60-300 seconds, and

pairs are stable. Private normalized set digests/counts, FIDs, and epochs never

## Source and private-state authority

Source mode `S` requires checkout `HEAD`, protected remote `main`, the workflow
input commit, the inert preparation binding, and the successful Verify SHA to
be identical. All 20 dispatcher operations are permitted in `S`; outside `S`,
only `A` is permitted and only `preflight`, `g001-current-state`,
`g002-live-inspect`, and `ptr-live-inspect` may run. The other 16 operation
names are S-only. Source mode `A` requires the exact activated binding, exactly
one parent equal to `S`, a raw NUL-safe three-path diff containing only regular mode-`100644`
`config/releases/0.4.0-sealed-launch.json`, `package.json`, and
`package-lock.json`, successful Verify at `A`, and binding/history
verification.

The existing subsystem-owned roots remain exactly the audit/private, runtime,
and cache roots under the production account home. Each root must already
exist, remain below the account home, be owner-owned mode `0700`, and have no
symlink component; the dispatcher neither creates nor repairs a root. It may
create only `sealed-realms-v1` children. Every state file is a canonical,
bounded, no-clobber, owner-owned regular single-link mode-`0600` file followed
by directory fsync. No public value contains an absolute private path.

Mutation authority requires a one-time confirmation consumed before the
mutation is released. Ambiguous results write reconciliation state that can
never reactivate the consumed confirmation. The corresponding existing
inspect operation exclusively proves adoption, resume, or no effect; submitted
publication or reducer calls are never replayed. Without adding an operation
name, `g001-policy-observe` owns inspection, confirmed cleanup, and adoption of

## Failure and rollback rules

The release fails closed on any identity collision, missing receipt, stale or
swapped evidence, dirty source, wrong toolchain digest, nonzero sealed state,
unexpected public table, owner-anchor mismatch, open admission path, or live
probe disagreement.

Before activation, failure leaves the existing `0.3.43` Pages artifact and
Genesis 001 database untouched. After activation, the retained exact `0.3.43`
Pages artifact is the client rollback target; rollback never republishes or
mutates Genesis 001 and never opens G002/PTR admissions. Cloudflare Worker
rollback uses an already attested predecessor version and is followed by the
same live suspension probes.

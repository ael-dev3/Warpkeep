# Warpkeep 0.4.0 sealed-realms release design

Status: owner approved on 2026-08-30

## Outcome

Warpkeep 0.4.0 ships a production launcher with three independently secured
realm choices:

| Realm | Version | Player access | New admissions | Purpose |
| --- | --- | --- | --- | --- |
| Genesis 001 | exact `0.3.43` forever | existing admitted players only | permanently closed | preserved live game |
| Genesis 002 | `0.4.0` | nobody | closed until a separately approved release | sealed Greater Realm |
| Public Test Realm (PTR) | `0.4.0-ptr.1` | one configured owner-admin only | no public admission surface | isolated testing of future patches |

The client exposes all three choices in a dedicated selector within the
`ENTER REALM` screen. Genesis 001 remains the default. A realm may be selected
for inspection even when entry is unavailable, but selection alone never
authenticates, admits, connects, or mutates backend state.

This design supersedes the two-choice outcome in
`2026-08-27-realm-chooser.md` and the earlier Greater Realm cutover plan. It
retains the sealed Genesis 002 design and extends it with a separate PTR and a
permanent Genesis 001 preservation boundary.

## Realm isolation

Each realm has a distinct full SpacetimeDB identity. Aliases are permitted only
as one-time publication inputs and human labels; clients, receipts, imports,
and production verification bind full lowercase 64-hex identities. Genesis
identities and the PTR identity must be pairwise distinct.

Genesis 001 keeps its existing database, data, player set, gameplay schema,
and `0.3.43` player-facing version. Genesis 002 and PTR are fresh databases
published from separate modules. No migration, table copy, database rename, or
republish may cross the three security domains.

### Genesis 001 preservation

Genesis 001 remains playable for identities already admitted at the freeze
boundary. All request, allow, admit, founder, disable, revoke, reset, auth-epoch,
relocation, deactivation, and re-enable writers fail before database or audit
effects. Legacy Greater Realm relocation and deactivation code must be removed
from the active release authority or guarded by a permanent refusal that is
covered by tests and release verification.

The exact live policy is:

- realm version `0.3.43`;
- existing-player access enabled;
- new admission and access requests disabled;
- the admitted set preserved;
- no realm relocation or deactivation;
- no future source publication to the Genesis 001 database.

Read-only status and observation remain available through the protected
administrator path. Public admission requests stay suspended at the auth
bridge before authentication, rate limiting, database access, or notification
delivery.

### Genesis 002 sealed realm

Genesis 002 uses the private `spacetimedb/genesis002` module and release
`0.4.0`. It contains the finalized selected Greater Realm atlas but has zero
players, admissions, founders, castles, claims, occupancy, activation rows,
Worker rows, and public tables. It exposes no player authentication, request,
admission, subscription, or entry route.

Only the bounded administrator atlas-import surface exists during launch.
Every writer proves zero population both before and after its effect and becomes
permanently inert after finalization. Future admission, activation, player
presentation, or founding requires a separate reviewed design and release.

### Public Test Realm

PTR uses the private `spacetimedb/ptr` module, alias `warpkeep-ptr`, module
identity `warpkeep-ptr-owner-view-v1`, atlas `PTR_GREATER_REALM`, and release
`0.4.0-ptr.1`.

PTR has no public admission or access-request surface. Its only player anchor is
the singleton owner FID supplied through the protected
`WARPKEEP_PLAYER_CANARY_OWNER_FID` secret. Entry requires a short-lived,
server-bound token with all of the following exact claims:

- PTR database identity;
- PTR realm and role;
- distinct PTR OIDC audience;
- configured owner FID;
- maximum lifetime of 120 seconds.

The Hermes administrator remains an operations principal, not a second player.
Any missing, additional, disabled, or mismatched owner anchor fails closed.
Later test players require a new reviewed access model.

## Client interaction

The `ENTER REALM` screen presents one keyboard-accessible, screen-reader named
selector containing `Genesis 001`, `Genesis 002`, and `Public Test Realm`.
Every choice has a text status and an icon/tooltip so color is never the only
signal.

- Genesis 001 shows available only for a currently authenticated, already
  admitted player. Entry reuses the existing `0.3.43` path.
- Genesis 002 always shows sealed. Entry performs no network or authentication
  action and displays the deterministic suspension notice.
- PTR shows available only after server-verified owner authority. Non-owner,
  anonymous, expired, checking, and error states remain locked and perform no
  database connection.

Realm selection is presentation state only. It is not stored in local storage,
query parameters, cookies, or any authority-bearing persistence.

## Auth bridge and Cloudflare boundary

The production Worker keeps public admission requests suspended for both
`POST` and CORS `OPTIONS` on `/v2/access/request`, returning exact HTTP 503 and
`admission_requests_suspended` before any downstream work.

PTR token minting is a separate fail-closed route and audience. Worker versions
are uploaded using predecessor-bound `keep_bindings` semantics and verified
against the exact predecessor and latest uploaded version. An ambiguous upload
or receipt state stops the release; it never authorizes a retry or activation.
Secrets, FIDs, private receipt bodies, and raw tokens must not enter repository
files, Pages variables, Actions logs, or public release bindings.

## Build and verification architecture

The required GitHub check name `verify` remains stable while hosting-platform
contracts run on their native operating systems:

1. Linux verifies unit/integration tests, typechecks, builds, dependency and
   source closures, SpacetimeDB modules, generated bindings, sealed-launch
   policy, Pages classification, and security checks.
2. The protected macOS ARM64 runner verifies the exact BSD `stat`/`ls` and
   owner-private B0/prepared bridge contract.
3. A final `verify` aggregator depends on both and fails if either fails, so
   branch protection continues to require the same context.

Tests must not depend on checkout directory names or unavailable ambient tools.
The pinned, checksum-verified SpacetimeDB 2.6.1 CLI is installed explicitly in
the Linux job. Production-only filesystem semantics are tested on macOS rather
than weakened to accept GNU substitutes.

Before merge and activation, run focused adversarial tests, the complete root
suite, auth-bridge checks, both SpacetimeDB module suites, generated-binding
diffs, TypeScript checks, production builds, `git diff --check`, CodeQL, and a
dependency/security audit. Every required status check must be green.

## Two-phase release

### Phase A: preparation PR

Repair PR #228 in place. Its package remains `0.3.43`; all live G002/PTR
identities and receipts remain null; `pagesDeploymentApproved` and all G002,
PTR, legacy-presentation, and notification gates remain false. Pages must
classify the merge as inert and skip deployment.

After verification and review, squash-merge #228 through protected `main` and
delete its branch.

### Phase B: protected operations

From the exact clean protected preparation commit:

1. revalidate the retained Genesis 001 freeze and current-player census proof;
2. prove the live admission suspension and permanent Genesis 001 policy;
3. publish Genesis 002 exactly once and record its fresh identity/receipt;
4. import and finalize the exact selected atlas, then prove zero population and
   private access;
5. publish PTR exactly once and record its fresh identity/receipt;
6. import/finalize the PTR atlas and provision exactly one owner anchor;
7. deploy and verify the prepared auth-bridge version with PTR bindings; and
8. generate the privacy-safe activation binding only from the complete,
   cross-checked private evidence envelope.

Possibly-submitted publication or import errors require read-only
reconciliation. They are never retried blindly.

### Phase C: activation PR

Create one minimal successor commit that changes the package/lock/release to
exact `0.4.0`, fills the generated public release binding, enables only PTR
presentation, and sets `pagesDeploymentApproved: true`. Genesis 002 player
presentation, legacy Greater Realm presentation, admission notifications, and
all admission gates remain false.

After all protected checks pass, squash-merge the activation PR. Pages verifies
the live suspension and identity bindings immediately before deployment, then
deploys and performs live smoke/security checks. Tag the exact verified main
commit `v0.4.0`. Merge or close every other open PR so the repository ends with
zero outstanding pull requests.

## Failure and rollback rules

The release fails closed on any identity collision, missing receipt, stale or
swapped evidence, dirty source, wrong toolchain digest, nonzero sealed state,
unexpected public table, owner-anchor mismatch, open admission path, or live
probe disagreement.

Before activation, failure leaves the existing `0.3.43` Pages artifact and
Genesis 001 database untouched. After activation, the retained exact `0.3.43`
Pages artifact is the client rollback target; rollback never republishes or
mutates Genesis 001 and never opens G002/PTR admissions. Cloudflare Worker
rollback uses an already attested predecessor version and is followed by the
same live suspension probes.

## Acceptance evidence

Completion requires authoritative evidence for every item below:

- protected `main` and `v0.4.0` point to the reviewed activation commit;
- GitHub Pages serves package `0.4.0` and the three-choice selector;
- Genesis 001 reports exact `0.3.43`, existing-player access, and permanently
  closed admission/relocation/deactivation writers;
- Genesis 002 has its distinct identity, finalized atlas, zero population,
  zero public tables, no player connection, and no admission surface;
- PTR has its distinct identity, finalized atlas, exactly one enabled owner
  anchor, owner-only token/connection success, and non-owner denial;
- the auth bridge returns the exact admission-suspended response and has the
  activated PTR bindings;
- all required GitHub checks and local verification commands pass;
- security review finds no unresolved critical or high-severity issue;
- the working tree is clean; and
- GitHub reports zero open pull requests.

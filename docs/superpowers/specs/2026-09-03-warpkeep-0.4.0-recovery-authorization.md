# Warpkeep 0.4.0 recovery authorization

Status: approved recovery design; final implementation review pending

Date: 2026-09-03

## Purpose

Ship the scoped 0.4.0 release without claiming that the unavailable Genesis
001 historical freeze-publish receipt was recovered. The release may rely on a
new, separately named administrative authorization only after that
authorization proves the exact release candidate, deployment artifact, target,
and current sealed-realm invariants.

This is a new provenance root for this release. It is not a recreated,
substitute, or reconstructed Genesis 001 receipt.

## Fixed product state

- Genesis 001 remains the existing `0.3.43` realm at database identity
  `c2001f161d44e50c0a75356d79a4d10fa4a9d77ea4eddd56cda7ac6af50b570e`.
- Existing Genesis 001 players retain access. Admission-state mutations and
  access-request submissions remain disabled.
- Genesis 002 remains sealed: no player access, admissions, access requests,
  activation writes, or player-facing route.
- PTR remains a separate realm and database. It admits only the configured
  singleton owner/admin path; general admissions and access requests remain
  absent. The checked-in auth-bridge default remains `PTR_ENABLED=false`; the
  recovery observer is callable only in an explicitly armed deployment whose
  configuration attests `PTR_ENABLED=true`. This is a prerequisite for reusing
  the existing PTR claim minting, never a recovery-only bypass of that gate.
- The Enter Realm screen retains distinct Genesis 001, Genesis 002, and PTR
  choices.
- The recovery work adds no admissions, gameplay, notification, observer,
  economy, travel, chat, or other product feature.

## Non-goals

- Do not manufacture bytes matching the historical receipt digest.
- Do not rerun the historical Genesis 001 freeze publication.
- Do not write a new receipt into the historical receipt path.
- Do not change Genesis 001's module, database identity, current player set, or
  admission policy.
- Do not weaken the existing full historical-evidence activation path.
- Do not use Cloudflare deployment history, SpacetimeDB policy metadata, Git
  history, or a user assertion as if it were the missing receipt body.
- Do not make the recovery signer an admission, player-session, database-write,
  or general administrative API.

## Authorization modes and compatibility

The existing schema-1 preparation and historical-receipt activation paths
remain byte- and behavior-compatible. If the exact historical receipt is later
recovered, the existing activation route remains valid without accepting any
recovery field.

The new route uses a separate schema and the literal mode
`recovery-authorization-v1`. Its historical Genesis 001 freeze receipt digest
and commitment are both `null`. No historical receipt parser, resolver, path,
or signature check is invoked for this mode. A recovery authorization can never
be accepted as a Genesis 001 receipt or as PTR, session, admission, or database
authority.

Mixed modes, implicit mode selection, schema downgrade, and recovery fields in
the historical mode are hard failures.

## Accepted trust root

Recovery deliberately establishes a new root of trust: the Cloudflare account
and the narrowly scoped people or service identities allowed to deploy the
release-recovery services or read/change their signing configuration. Anyone
with that authority can replace signer code or use its runtime key and is
therefore an authorized recovery release signer. Compromise of that authority
is a compromise of this recovery root.

A Cloudflare Worker secret is available to the Worker at runtime. The design
does not describe it as a hardware-backed, non-exportable, or Cloudflare-held
KMS key. A managed non-exportable KMS may replace the Worker secret later, but
0.4.0 does not depend on an unimplemented property.

The recovery service is isolated from the normal auth bridge:

1. `warpkeep-release-recovery-gateway` owns the narrow public release endpoint.
   It holds no signing key, SpacetimeDB credential, GitHub App credential, or
   ledger binding. It accepts only bounded release protocol requests and
   forwards them over one explicit Cloudflare Service binding.
2. `warpkeep-release-recovery-signer` has no public route or browser endpoint.
   It is reachable only through that Service binding. It validates the raw
   GitHub OIDC token itself, gathers authoritative evidence, signs, and owns the
   ledger binding.
3. `ReleaseRecoveryAuthorizationLedger` is one SQLite-backed Durable Object
   namespace used only by the signer. A fixed control-named instance owns the
   enabled epoch, while one request-named instance owns each server-side arming
   tuple, issuance state, and reconciliation state. KV, process memory,
   Worker-variable propagation alone, and caller-provided replay state are not
   accepted as the single-use record.
4. `warpkeep-auth-bridge` exposes only a privacy-safe release-status and
   live-realm observation RPC to the signer through a Service binding and a
   dedicated RPC credential. It exposes no new public route, token, admission
   method, or database writer. The named entrypoint has one method and no
   `fetch` handler. Its request profile is
   `warpkeep-release-recovery-realm-observation-request-v1`; its credential
   and census pepper are distinct canonical unpadded base64url encodings of
   exactly 32 random bytes. Every failure crossing this RPC boundary is the
   single detail-free error `RELEASE_RECOVERY_OBSERVATION_FAILED`.

Cloudflare account membership and deployment tokens for these services must be
restricted independently from ordinary Worker development. The signer key,
read-only GitHub App credential, and signer-to-bridge RPC credential are
dedicated to this service and are not shared with OIDC, sessions,
notifications, or any database writer. The signer retains no SpacetimeDB owner
token or long-lived Hermes administrator secret.

No Worker receives another Worker's secret merely to compare it. The bridge
checks both constant-work exact wire-value equality and representation-aware
underlying bytes for the RPC secret, census pepper, and only the
signing/admin/session/optional-notification material it already owns. Canonical
base64url/JWK values are decoded; opaque strings are compared as UTF-8 bytes, so
reuse of the 43-character RPC wire value as an opaque secret is also rejected. The
signer compares the decoded RPC secret with `RECOVERY_SIGNING_PRIVATE_JWK.d`.
The owner-private bootstrap, which already has provisioning authority for both
Workers, additionally compares the recovery signing scalar, RPC secret and
census pepper without printing or copying them and emits only pass/fail plus
the final computed configuration identity. RPC authentication itself uses a
constant-work SHA-256/XOR comparison, never ordinary secret-string equality.

The projection includes every static realm invariant and all non-historical
receipt commitments. It excludes no caller-selectable policy field. There is no
JWS, JWS digest, live evidence body, or live evidence commitment in the
checked-in file.

The schema-2 binding has its own exact key list, parser, and commitment
projection. All bridge deployment/config fields and all three expected program
pins above are included in that key list and in the
`recoveryAuthorizationCoreSha256` projection. They must equal the independently
configured server arming tuple before its Durable Object row can be installed.
Schema 1 remains byte-for-byte unchanged. To keep the schema-2
commitment graph acyclic, every schema-2 receipt commitment is computed with
`recoveryAuthorizationCoreSha256` forced to `null`; after every remaining
receipt commitment is populated, the recovery core is computed over the full
schema-2 binding with only its own core slot forced to `null`. The preparation
commit and tree may be fixed in this core. The later activation candidate commit
and tree are never inputs to the checked-in core; they are verified and bound at
runtime by the JWS.

The sequencing interlock is exact: first freeze the complete preparation parent;
then a separate deployment authority deploys the recovery-capable bridge/signer/
gateway with bridge `PTR_ENABLED=true` for the pre-existing owner-only observer
path but signer `RECOVERY_ENABLED=false`; then authenticated Cloudflare readback supplies
the actual bridge Version Metadata UUID and confirms disabled config, limits,
bindings and source digest; only then may one local transaction generate the
schema-2 binding, root package/lock version `0.4.0`, and matching host-private
disabled arming manifest. The activation candidate is the single child of the
preparation parent and changes exactly those three repository files. Packaging
uses that activation child, never the `0.3.43` preparation parent.

The recovery key ID and thumbprint are compile-time verifier constants. A
dynamically returned JWK, `kid`, URL, certificate, or thumbprint is never a
trust input.

The exact public P-256 JWK is checked into both the Worker and local-verifier
source closures. Signer startup derives the public coordinates and RFC 7638
thumbprint from its private JWK and requires byte-for-byte equality with those
pinned constants before status or signing is available.

## Workflow identity

The gateway receives a GitHub Actions OIDC token with the dedicated audience
`warpkeep-release-recovery`. The private signer verifies the token directly
against GitHub's issuer and JWKS and requires exact claims for:

- subject `repo:ael-dev3/Warpkeep:environment:github-pages`, repository name,
  numeric repository ID, owner ID, protected main ref, `sha`, event,
  environment, workflow name/ref/SHA, check-run ID, and local-runner identity;
- the expected `Deploy GitHub Pages` workflow and `github-pages` protected
  environment, with `ref_protected` true and `runner_environment`
  `self-hosted`;
- the candidate commit as current protected main and as both `sha` and
  `workflow_sha`; the signer resolves `check_run_id` through GitHub and requires
  the exact `deploy-recovery` job;
- canonical decimal Pages run ID and run attempt values, which become part of
  the authorization and ledger key. The source Verify run ID and attempt are
  separate locators; the signer requires the exact Verify workflow, `push`
  event, main branch, successful conclusion, and candidate head SHA through
  GitHub's API.

An OIDC token from a pull request, fork, other ref, other workflow, other
environment, stale main commit, or different repository is denied. The public
gateway does not convert transport reachability into identity; the signer
performs the identity decision on every issue, claim, completion, or
reconciliation call.

Local-execution amendment (2026-09-07): the active release goal requires Windows/
WSL production execution and supersedes the earlier GitHub-hosted recovery job
requirement. The independently fetched selected job must have exactly the label
set `self-hosted`, `Linux`, `X64`, `warpkeep-production-admin`, and
`warpkeep-repository-exclusive`, assigned runner name `warpkeep-wsl-production-01`,
group name `Default`, and positive canonical runner/group IDs. API label order
is immaterial; extra, missing, duplicate, Mac, ARM64, hosted, or unassigned
selected-runner metadata is rejected. The name is the chosen provisioning

The repository's sole observed runner at amendment time was the offline Mac
runner. Registration of the dedicated local runner, its actual metadata,
isolation, protected workflow execution, and real signed-token compatibility
must therefore be verified before deployment. Labels and local environment
variables alone are never identity: GitHub signature verification and exact

The protected recovery job source must request that same exact label set and
the `github-pages` environment. Its explicit permissions are `contents: read`,
`actions: read`, `pages: write`, and `id-token: write`, with no additional grants.
The workflow retains the fixed `warpkeep-production-state` concurrency group
with cancellation disabled. Recovery job-level concurrency, matrices, reusable
workflow substitution, additional job containers/services, and ignored job
failure are rejected. These source checks complement, not replace, GitHub's
independently authenticated assigned-runner and OIDC evidence.

The ledger's stable workflow identity projection is every verified workflow
identity field except the OIDC token's `jti`. Raw token bytes and the OIDC
`jti`, `iat`, `nbf`, and `exp` claims are ephemeral authentication material,
not idempotency identity. Every call independently verifies a fresh token; an
explicit issue retry may differ only in those ephemeral values and must match
the original request locators and every stable identity field exactly. It
returns the already retained authorization bytes without signing again or
extending any time. A changed locator or stable identity field is denied.

Gateway and signer RPC request objects use exact ordered key lists. Issue is
`requestId, candidateCommit, sourceVerifyRunId, sourceVerifyRunAttempt,
artifactId, oidcToken`; claim appends `authorizationJws`; completion and
reconciliation append `claimReceiptJws` to the issue list, not to the claim
list; `authorizationJws` is therefore forbidden after claim. Terminal lookup is only `requestId`;
status has no argument or body. Success objects contain exactly one of
`statusJws`, `authorizationJws`, `claimReceiptJws`, or `terminalJws` as
appropriate. The public gateway parses no token/JWS, accepts no query string,
uses a 32 KiB POST body cap and returns only no-store JSON. Its safe log schema
is exactly `schemaVersion, profile, endpoint, outcome, httpStatus, requestId`
with fixed enums and no exception text or arbitrary metadata.

## Independent evidence collection

The caller supplies locators only: request ID, candidate commit, GitHub run and
artifact identifiers, and the raw OIDC token. It does not supply a trusted
commit tree, digest, policy value, database identity, evidence commitment, or
release result.

The signer independently obtains and verifies:

1. Through its read-only GitHub App identity: protected-main ref, commit,
   single-parent ancestry, tree, checked-in recovery binding, protected workflow
   bytes, the exact activation delta from the server-armed preparation tree,
   same-run Pages artifact, and artifact metadata. The signer does not make one
   GitHub request per source-closure member. The complete source closure remains
   locally verified and its preparation digest is pinned in the server-side
   arming tuple.
2. Through the auth bridge's internal Service-binding RPC: exact deployed
   bridge service, semantic worker version, actual Cloudflare Worker version
   ID, source commit, configuration identity and configuration epoch, closed
   public admission-request state, and fresh realm
   observations. The request is exactly
   `{schemaVersion:1, profile:"warpkeep-release-recovery-realm-observation-request-v1", rpcCredential, requestId, candidateCommit, recoveryAuthorizationEpoch}`
   with no other receiver-visible own key. The response echoes request ID,
   candidate commit and recovery-authorization epoch exactly; they are binding
   coordinates and are not aliases for the independently returned bridge
   worker/source/config values. The bridge mints and consumes any
   short-lived SpacetimeDB inspection token inside the RPC; no token or
   underlying secret crosses into the signer. Because the frozen Genesis 001
   ABI cannot gain a new principal, its observation uses the existing Hermes
   administrator JWT. Genesis 002 and PTR observation likewise remains inside
   the bridge's fixed, exact-parsed implementation; no administrative token
   crosses the Service binding.
   The semantic worker version is source-fixed, while the actual current
   Worker version ID comes only from Cloudflare's `CF_VERSION_METADATA.id`.
   The signer requires semantic version, Worker version ID, source commit,
   computed configuration identity and configuration epoch to equal both the
   checked-in binding and the independently installed arming tuple; a returned
   or deploy-supplied value cannot authorize itself.
3. Through the fixed observer and the signer's own public schema fetches: the
   Genesis 001 policy and complete admitted census, empty/sealed Genesis 002
   state, PTR singleton-owner/sealed state, and deployed schema/ABI descriptions
   for all three realms. No current database module is described as providing a
   truly read-only principal: the bridge confines the existing short-lived
   administrative capability to the fixed observation implementation and
   returns only a bounded normalized snapshot.

The bridge computes configuration identity with the standard recovery length-
framed SHA-256 and terminal-LF domain
`warpkeep.release-recovery.bridge-config.v1\n`. Its flat canonical JSON payload
has exactly this key order: `schemaVersion`, `profile`, `bridgeWorkerVersion`,
`bridgeSourceCommit`, `bridgeConfigEpoch`, `spacetimeOrigin`,
`genesis001Database`, `genesis002Database`, `ptrDatabase`,
`genesis001Audience`, `genesis002Audience`, `ptrAudience`, `ptrEnabled`,
`signingPublicJwkThumbprint`, `rpcCredentialSha256`, `censusPepperSha256`,
`canaryFidHmacSha256`. The canary commitment is keyed by the census pepper with
the common HMAC framing: domain bytes are UTF-8
`warpkeep-recovery-v1:warpkeep.release-recovery.bridge-config.canary-fid.v1\n:`,
the payload is UTF-8 canonical-decimal FID, and the HMAC input is
`U32BE(domainBytes.length) || domainBytes || U64BE(payload.length) || payload`;
only the final
configuration identity leaves the bridge. There is no
`RELEASE_RECOVERY_BRIDGE_CONFIG_IDENTITY` setting. A changed observer setting,
secret, canary, source or epoch necessarily changes the computed identity.
The exact values include `schemaVersion:1`, profile
`warpkeep-release-recovery-bridge-config-v1`, semantic version
`warpkeep-auth-bridge-release-recovery-v1`, origin
`https://maincloud.spacetimedb.com`, audiences `warpkeep-spacetimedb`,
`warpkeep-genesis-002-spacetimedb`, and `warpkeep-ptr-spacetimedb`, and
`ptrEnabled:true`; the remaining public coordinates use their exact parsed
values and the three private inputs enter only through the commitments above.

Task 4 validates the original pre-clone request and rejects proxies, accessors,
exotic prototypes, symbols, inherited or nonenumerable properties before the
Service-binding call. The Task 3 receiver can validate only the structured
clone's receiver-visible prototype, own enumerable string keys, values and
canonical size; it must not claim to detect caller-side structure erased by the
clone. Receiver-reached failures use one fresh detail-free error. Task 4 also
remaps structured-clone, binding-dispatch and other failures raised before
receiver method entry to its own detail-free observation error.

The signer recomputes the binding projection, commit tree, source-closure
profile relationship, activation delta, canonical Pages artifact digests, and
privacy-safe live evidence digests. The full preparation closure digest comes
from both the checked-in core and independently armed server state, while local
Verify recomputes all closure members. It accepts no caller-selected reducer,
procedure, query, URL, identity, publish, mutation, or database-owner token.
The only SQL texts are the source-fixed literals `SELECT program_hash FROM
st_module` and `SELECT fid FROM player_v2`. Each is sent as the exact UTF-8 body
of authenticated `POST
/v1/database/<fixed-lowerhex64-identity>/sql?confirmed=true` with
`Content-Type: text/plain; charset=utf-8`, `Accept: application/json`, and
`Cache-Control: no-store`. Procedure calls are authenticated `POST
/v1/database/<fixed-lowerhex64-identity>/call/<fixed-procedure>` with exact
`application/json` positional-array bodies: `[]`, or `[<canonical-decimal-fid>]`
for the one member call. Fetch uses manual redirect handling, exact final-URL
equality, no retry, and accepts only status 200 with JSON media type. No caller
value selects a database identity, URL, procedure, query or argument other than
the validated request-binding coordinates.

The program query never selects `program_bytes`. Its response is exactly one
SQL statement result, whose schema has exactly one named `program_hash` column
of SATS `U256`, and exactly one one-element row. The U256 wire value is a
canonical lowercase Ethereum quantity matching
`^0x(?:0|[1-9a-f][0-9a-f]{0,63})$`. Parse it as a 256-bit unsigned integer,
left-pad its big-endian hexadecimal magnitude to 32 bytes, reverse those 32
bytes because `Hash::to_u256` interprets the stored hash bytes little-endian,
and expose the resulting exact conventional 64-lowerhex Keccak-256 current-
program hash. Keccak-256 is not NIST SHA3-256. Before and after values for each
realm must be equal. Task 4, not caller input, compares each stable value with
the same expected pin in the checked-in core and server arming tuple. Expected
pins are derived before production access from two byte-identical clean builds
under the distinct `warpkeep-release-recovery-cross-platform-program-build-v1`
profile. It is not represented as the historical Darwin/arm64 publisher build.

For a census of `N` players, the bridge performs exactly `N + 14` no-retry
SpacetimeDB requests. First it reads current program hashes for G001, G002 and
PTR as one group with at most three concurrent requests. It then performs the
existing `N + 8` sequence: G001 policy; G001 alpha status before; the fixed FID
query; one fixed admission-status procedure per FID; the same query again;
G001 alpha status after; G002 administrator status; PTR administrator status;
and PTR owner status under a token bound to the configured G001 canary FID and
its just-observed auth epoch. Finally it repeats the G001/G002/PTR program-hash
group. Groups and the member pool never overlap. `N` is `1..100`, exactly the
G001 player capacity; member calls use at most six concurrent connections,
understood as the shared top-level Service-binding-chain limit. The signer
finishes its sequential schema fetches before starting this RPC and awaits it
without other outbound header waits. Immediately after synchronous request
capture, the bridge creates a request-context 75-second timeout signal and
records an absolute deadline using the Workers runtime's I/O-updated clock.
Cloudflare freezes both `Date.now()` and `performance.now()` between I/O, so
neither is treated as an independent monotonic clock; integer Unix seconds are
captured separately only for evidence and CPU is bounded by the Worker CPU
limit. Each request races the overall signal and a fresh four-seconds-or-
remaining timeout. Timer firing or I/O-updated late completion fails closed.
There are at most 114 upstream requests and at most 12 MiB of aggregate
upstream response bytes, and a 64 KiB canonical RPC response. It never retries
and aborts all active work on the first failure.

All SATS integer tokens are parsed losslessly from their original JSON lexeme
into `BigInt`: canonical unsigned decimal only, bounded to the declared `u32`
or `u64`, and never first rounded through `JSON.parse` number semantics. FIDs
are additionally `1..Number.MAX_SAFE_INTEGER`; canonical HMAC projections use
decimal strings. Each SQL response has one exact statement/schema shape, and
the FID rows each have one `U64` element. Since the fixed query has no `ORDER
BY`, the observer rejects duplicates and sorts the validated FIDs numerically
before comparing the two enumerations; it does not assume server row order.

`enabled` with a positive `u32` auth epoch and an internally valid request-state
tuple: request-cycle and requested-at options have identical presence, a present

`1..2^64-1`, absence implies `not_requested`, and presence implies `resolved`.

## Runtime authorization JWS

The signer issues an ES256 compact JWS only after independent validation. It
uses a dedicated P-256 key and never reuses the normal OIDC signing key, session
key, notification secret, SpacetimeDB token, or GitHub credential.

The protected header has exactly these fields, serialized in this order:

1. `alg`: `ES256`;
2. `typ`: `warpkeep-0.4.0-recovery-authorization+jwt`;
3. `kid`: the compile-time pinned recovery key identifier.

The other three signed object headers use the same exact `alg`, `typ`, `kid`
order and key restrictions. Their exact `typ` values are:

- `warpkeep-0.4.0-recovery-status+jwt`;
- `warpkeep-0.4.0-recovery-claim+jwt`;
- `warpkeep-0.4.0-recovery-terminal+jwt`.

Algorithm/key URLs, embedded JWKs or certificates, critical extensions, and
extra fields are forbidden. The signature is exactly 64-byte IEEE-P1363 P-256
ECDSA. The issuer normalizes `s` to the lower half of the curve order and every
verifier rejects a high-S alternative.

The payload is canonical UTF-8 JSON with exact ordered keys and no duplicate,
accessor, inherited, or extra fields. It contains:

- protocol identity: schema version, profile, issuer, audience, subject, key
  ID, request ID, random JWS `jti`, and authorization epoch;
- GitHub identity: repository and immutable repository/owner IDs, protected
  ref, workflow ref/SHA, environment and event; the Pages workflow run ID and
  attempt from OIDC; and the distinct successful source Verify run ID and
  attempt verified through GitHub's API;
- candidate identity: predecessor commit, candidate commit, candidate tree,
  source-closure profile/digest, binding-core digest, Pages artifact ID and
  name, GitHub artifact archive digest, inner artifact TAR digest,
  content-manifest digest, deployment-attestation digest, release version,
  operation, and canonical origin;
- service targets: exact auth Worker name and exact G001, G002, and PTR database
  identities;
- historical status: literal `unavailable` and expected digest
  `5a9629c7ee695abc2b2369921274dcaa9c618b747387b90f9444429ab8e81d63`;
- fixed G001 `0.3.43` access/no-admission invariants and the historical
  `g001BaselineAbiSha256`, with deployed v10 ABI and current-program identities
  committed separately inside `liveInvariantDigest`; G002 sealed/empty
  invariants and PTR singleton-owner/no-admission invariants;
- the signer's issuance observation interval, issuance snapshot digest, and
  stable `liveInvariantDigest`;
- safe integer `iat`, `nbf`, and `exp` values.

There is no backdating. `nbf` equals `iat`, `exp - iat` is at most 15 minutes,
and issue occurs in the protected deployment job immediately before claim. A
status, clock, or evidence freshness disagreement is a hard failure.

The JWS is owner-private runtime authority. It is never checked in, uploaded as
an artifact, printed, included in a workflow output/summary, or returned in an
error. It exists only in a mode-0600 runner file or process memory, is verified
and claimed in the same protected job, and is deleted before the external
deployment action starts. Only its SHA-256 digest, `jti`, and request ID may
cross the private step boundary.

## Build and live deployment identity

The build creates one deterministic public
`/.well-known/warpkeep-deployment-v1.json` attestation before Pages packaging.
It contains the candidate commit/tree, binding-core and source-closure digests,
release version, canonical origin, and a canonical content-manifest digest over
every regular `dist` file except the attestation itself. The content manifest
uses sorted normalized paths, byte lengths, and SHA-256 digests; it rejects
links, devices, duplicate/case-colliding paths, hidden authority files, and
unlisted content.

The recovery upload uses the exact name
`github-pages-recovery-<pages-run-id>-<pages-run-attempt>`. Its numeric artifact
ID comes from the pinned Pages upload action and the same exact name is passed to
the pinned deploy action. The signer downloads that immutable same-run artifact
by numeric ID using its own read-only GitHub App credential. It validates a
bounded streaming ZIP containing the sole `artifact.tar`, then validates that
TAR incrementally with compressed/uncompressed byte, entry-count, path, mode,
type, long-name, duplicate, and case-collision limits. It never buffers the
roughly 125 MB artifact in one `ArrayBuffer`. Fetch plus parsing has one exact
300-second end-to-end cap, a 30-second idle cap, 160 MiB compressed cap, and 150
MiB TAR cap; only after it finishes does the distinct 90-second live-evidence
allocation begin. The runtime JWS separately binds
the GitHub artifact archive digest, inner TAR digest, content-manifest digest,
and deployment-attestation digest.

Postflight does not treat HTTP 200 or a JavaScript substring as deployment
proof. The signer independently checks the successful GitHub Pages deployment
for the exact repository, environment, Pages run/attempt and candidate SHA,
then requires the exact local `deploy-recovery` job and one earlier step named
`Deploy recovery-authorized release to GitHub Pages`; that step must have
`status: completed` and `conclusion: success`. The jobs API does not expose the
step's `uses` value, so the independently fetched candidate workflow bytes must
prove that this unique step uses
`actions/deploy-pages@cd2ce8fcbc39b97be8ca5fce6e763baed58fa128`. During the same job,
completion/reconciliation requires the enclosing job still `in_progress` with
null conclusion; after the job ends, an alarm or read-only reconciliation may
observe any overall job conclusion, but the exact successful deploy step remains
mandatory. The signer then fetches the no-store public deployment attestation
from `https://warpkeep.com`. Its bytes and fields must exactly match the
attestation already validated inside the claimed artifact. The existing live
verifier still performs its broader asset, Mini App, auth, and realm checks.
Only the exact deploy-step evidence, matching GitHub deployment record and exact
live attestation can complete the ledger.

## Single-use ledger

The SQLite-backed `ReleaseRecoveryAuthorizationLedger` Durable Object owns one
row per checked-in request ID and enforces these monotonic states:

`armed -> issuing -> issued -> claimed -> completed`

It also permits `issuing -> expired-unused`, `issued -> expired-unused`, and
terminal `not-deployed`, plus a
non-terminal `reconciliation-required` state after ambiguous interruption. No
state returns to `issued` or `claimed`.

Before recovery enablement or issuance, the Cloudflare recovery root configures an exact arming
manifest under signer deploy authority. It contains request/core, preparation
commit/tree, complete closure profile/digest, epoch/key, release target, all
service/database identities, expected bridge semantic version, Cloudflare
Worker version ID, source commit, computed configuration identity/epoch, all
three expected program Keccaks, and every G002/PTR atlas coordinate. The static
protected realm-binding projection deliberately excludes the later activation
candidate commit/tree. The arming tuple contains that exact projection plus
only the two source-fixed binding/workflow paths; candidate coordinates are
verified separately from GitHub. The signer exact-parses the fixed
configuration, requires every shared projection field to be canonically byte-
equal to the protected binding, and transactionally installs every field once
in the immutable request Durable Object row; the gateway cannot supply or
change it and a later mutable Worker variable cannot replace it. The fixed
control object owns `enabled` and current epoch; each
request row snapshots the exact armed epoch. A missing, disabled, changed, or
conflicting arming tuple fails closed.

There is no public control endpoint. On every status or request operation, the
route-less signer exact-parses its deploy-controlled `RECOVERY_ENABLED`,
`RECOVERY_AUTHORIZATION_EPOCH`, and arming manifest and invokes an internal
monotonic control reconciliation. It may disable the current epoch or advance
to a higher disabled epoch; it can never decrease the epoch. Re-enabling an
epoch requires an exact new, unused request/arming tuple under the same
Cloudflare deploy trust root. Advancing/disabling makes old `armed`/`issued`
rows unusable because every issue/claim consults the control object; consumed
`claimed` rows remain read-only reconciliation records.

Issuance first transactionally reserves the exact request as `issuing`, with a
fixed payload, `jti`, validity window, caller/run identity, and evidence. After
signing, finalization atomically records the request ID, JWS `jti` and digest,
exact candidate/action/target, both workflow run identities, artifact digests,
evidence snapshot digest, stable invariant digest, epoch, and validity window.
The same request ID cannot produce a second usable JWS, including after expiry.
An interrupted `issuing` row may resume only the exact stored unsigned payload;
it can never alter its time, identity, evidence, or `jti`.

The issuing reservation stores an exact deadline 120 seconds after reservation.
Its alarm transitions a still-issuing row to `expired-unused` and deletes the
reserved payload; it never re-arms or reissues. The issued alarm is the fixed
JWS expiry and likewise deletes retained JWS bytes on `expired-unused`. Alarm
repair restores only the deadline already stored in the row and never extends
it.

Until claim or expiry, the ledger retains the exact short-lived JWS bytes only
to make an ambiguous issue response idempotent. An explicit retry must
independently verify a fresh OIDC token, match the exact original request
locators and stable workflow identity projection, and may then receive those
same bytes; it never causes another signature or extends time. Only raw token
bytes and their ephemeral OIDC `jti`/time claims may differ. Claim or expiry
deletes the retained bytes. A different stable identity, request locator, run,
artifact, or candidate is denied.

Claim performs fresh GitHub, artifact, auth-bridge, and SpacetimeDB validation
before a synchronous transaction changes `issued` to `claimed`. It requires the
exact private JWS and exact recorded run identity. The workflow must receive a
durable successful claim before invoking `actions/deploy-pages`. Repeated,
parallel, mismatched, expired, or partially recorded claims are denied.

A successful claim returns a second canonical ES256 object with type
`warpkeep-0.4.0-recovery-claim+jwt`. It binds the authorization request ID,
JWS `jti` and digest, run/attempt, candidate commit/tree, artifact ID and
digests, action/target, epoch, claim sequence, `claimedAt`, and
`claimDeadline`. It contains no raw authorization or evidence. The local
verifier checks this signed claim receipt with the same compile-time key and
requires a maximum two-minute receipt lifetime before allowing the deployment
step, with the hard boundary `nbf <= now < exp`. An unsigned gateway response
can never represent a successful claim. Post-deploy completion has different,
non-authorizing semantics: a separate signer-private parser, never a
caller-controlled expiry mode on the local/generic verifier, verifies the
receipt's canonical signature/payload and exact stored-row binding even if its
two-minute `exp` has passed, but only while `now < claimDeadline`, where the
signed and stored `claimDeadline === claimedAt + 1200`; it rejects at or after
that deadline. An expired receipt can never
start deployment, and an alarm reconciles from the stored consumed row without
receiving a receipt.

The claim payload has exactly these keys in this order: `schemaVersion`,
`profile`, `iss`, `aud`, `sub`, `kid`, `requestId`, `authorizationJti`,
`authorizationJwsSha256`, `pagesRunId`, `pagesRunAttempt`,
`sourceVerifyRunId`, `sourceVerifyRunAttempt`, `candidateCommit`,
`candidateTree`, `artifactId`, `artifactName`,
`githubArtifactArchiveSha256`, `innerArtifactTarSha256`,
`contentManifestSha256`, `deploymentAttestationSha256`, `operation`,
`canonicalOrigin`, `authorizationEpoch`, `claimSequence`, `claimedAt`,
`claimDeadline`, `iat`, `nbf`, and `exp`. Its profile and subject are
`warpkeep-0.4.0-recovery-claim-v1` and
`warpkeep-0.4.0-recovery-deployment-claim`. `nbf === iat`, `exp - iat <= 120`,
and `exp <= claimDeadline`; the signed two-minute `exp` is independent of the
20-minute ledger reconciliation deadline.

Before entering `issuing`, the Durable Object successfully schedules a bounded
reservation alarm; before storing JWS bytes as `issued`, it successfully
replaces that alarm with the authorization-expiry alarm. A failed or crashed
reservation therefore cannot leave an unbounded `issuing` row, and exact JWS
bytes are never durable without an expiry alarm. Claim atomically deletes JWS
bytes and sets `claimDeadline` to 20 minutes after `claimedAt` while the existing
expiry alarm remains installed, then replaces that alarm with the claim alarm
before returning success. A crash leaves either the earlier safe alarm or the
new claim alarm. Every later read repairs a missing or wrong nonterminal alarm.
A normal completion changes the row first and then cancels the alarm; a leftover
terminal alarm is a no-op. If the row is still `claimed` when the alarm fires, the alarm
first changes it to `reconciliation-required` and then performs only read-only
GitHub Pages and public-origin checks. Definitive proof of the exact deployment
marks it `completed`; definitive proof that no matching deployment occurred
marks it terminal `not-deployed`. An outage or ambiguous result leaves it
`reconciliation-required`. Automatic read-only retries occur after 1, 5, 15,
and 60 minutes and then stop. A later rerun or higher run attempt may read only
the signed terminal/request state; it cannot invoke reconciliation, issue,
claim, or deploy because its stable run/attempt identity differs. No
reconciliation path restores release authority.
`not-deployed` requires an authoritative terminal GitHub run/attempt whose
Pages deployment step never started plus absence of a matching Pages
deployment; elapsed time or a temporarily missing live marker is never enough.

After deployment, the signer independently checks the exact successful deploy
step, GitHub Pages deployment and `https://warpkeep.com` deployment attestation
before changing `claimed` to `completed`. It never waits for the same enclosing
job to report overall success while that job is still executing the completion
call. A runner crash, timeout, network ambiguity, or missing postflight therefore
cannot leave a reusable claim or silently become success.
A new attempt after either an expired or claimed authorization requires a
reviewed activation commit with a new request ID.

## Status, revocation, and public evidence

The gateway exposes a no-store, short-lived status document signed by the
private signer and containing only protocol identity, `enabled`, the positive
authorization epoch, and issue and expiry times. It publishes no JWK, key URL,
database value, player value, or release authority. Verifiers authenticate it
only with the compile-time pinned key and key ID. Changing the epoch or
disabling recovery invalidates `armed` and `issued` authority and any claim
receipt not yet accepted at the local deployment boundary. The workflow
re-reads and verifies signed status immediately after claim and again
immediately before invoking the Pages action. Once the Pages API request may
have been submitted, revocation cannot undo it; the already-consumed row never
regains authority and read-only completion/reconciliation continues under its
stored epoch so the ledger records the real outcome.

The status payload has exactly these keys in this order: `schemaVersion`,
`profile`, `iss`, `aud`, `sub`, `kid`, `enabled`, `authorizationEpoch`, `iat`,
`nbf`, and `exp`. Its profile and subject are
`warpkeep-0.4.0-recovery-status-v1` and
`warpkeep-0.4.0-recovery-control-status`; `nbf === iat` and `exp - iat <= 60`.

After `completed`, the signer may publish a signed terminal attestation with
only request ID, JWS digest and `jti`, candidate commit/tree, artifact digest,
operation/target, run identity, completion time, and terminal outcome. It never
publishes the raw JWS or live evidence. This attestation is audit evidence, not
reusable authority.

The terminal payload has exactly these keys in this order: `schemaVersion`,
`profile`, `iss`, `aud`, `sub`, `kid`, `requestId`, `authorizationJti`,
`authorizationJwsSha256`, `candidateCommit`, `candidateTree`, `artifactId`,
`artifactName`, `githubArtifactArchiveSha256`, `innerArtifactTarSha256`,
`contentManifestSha256`, `deploymentAttestationSha256`, `operation`,
`canonicalOrigin`, `pagesRunId`, `pagesRunAttempt`, `sourceVerifyRunId`,
`sourceVerifyRunAttempt`, `authorizationEpoch`, `completedAt`, `outcome`,
`iat`, `nbf`, and `exp`. Its profile and subject are
`warpkeep-0.4.0-recovery-terminal-v1` and
`warpkeep-0.4.0-recovery-terminal-attestation`; `outcome` is exactly
`completed` or `not-deployed`, `nbf === iat`, and `exp - iat <= 900`.

The private authorization JWS appears only in the authenticated, no-store issue
response for the exact verified workflow run and an exact idempotent retry. It
is absent from unauthenticated status/request inspection, errors, logs, workflow
outputs, summaries, artifacts, terminal attestations, and every browser-facing

## Release binding and verifier behavior

In recovery mode:

- `pagesDeploymentApproved` means the checked-in candidate may enter the
  protected recovery lane; it is not sufficient to perform a deployment;
- historical Genesis 001 freeze receipt digest and commitment remain `null`;
- all non-historical Genesis 001 state checks remain exact;
- all existing G002 and PTR database-identity, receipt, population, owner,
  presentation, and no-admission checks remain mandatory;
- the checked-in core fixes the exact repository, workflow, environment,
  operation, service/database targets, key, epoch, and static candidate
  invariants;
- static source classification produces a distinct recovery lane;
- the production side effect is unreachable until short-lived JWS verification
  and durable claim both succeed immediately before it.

The local verifier checks strict JWS bytes, pinned key and key ID, issuer,
audience, subject, lifetime, epoch, exact GitHub run identity, candidate commit
and tree, predecessor/ancestry, source closure, binding core, artifact and
content-manifest digests, missing historical status, service targets, realm
invariants, issuance snapshot freshness, stable live-invariant equality, and
the signed ledger claim receipt.

The activation generator receives either the complete historical evidence set
or a recovery-core candidate plus every remaining authenticated release record.
It never receives a runtime JWS and never writes or resolves a historical G001
receipt body in recovery mode.

## Protected workflow

The existing verified-main Pages flow gains a distinct recovery lane:

1. Check out the exact successful Verify SHA and prove it is current protected
   `main`, clean, single-parent, and the expected activation child.
2. Verify all static release evidence and the checked-in recovery core.
3. Build once with the pinned toolchain, generate and verify the deterministic
   deployment attestation, upload the one exact uniquely named Pages artifact,
   and retain its run-scoped numeric artifact ID.
4. In the `github-pages` protected environment, request a GitHub OIDC token for
   audience `warpkeep-release-recovery` immediately before issue. Ask the
   gateway to issue the private JWS; the signer independently fetches the
   repository/artifact and all live evidence before signing. Erase that token
   after the response; its lifetime is never assumed to cover claim.
   Before requesting authority, preflight the provisioned empty owner-private
   Linux handoff directory. Do not consume a one-use claim with known-unavailable
   persistence. This preflight does not replace the subsequent exclusive write
   and durability checks.
5. Verify the JWS locally with the compile-time key. Immediately before claim,
   request a different fresh custom-audience OIDC token. The signer repeats live
   validation and transactionally records the claim. Erase the claim token after
   the response, verify the signer's short-lived claim receipt while
   `nbf <= now < exp`, erase the raw authorization JWS, durably persist the
   verified private claim before any further network wait, and verify freshly signed
   enabled/epoch status before continuing.
6. Re-read signed enabled/epoch status and re-run the strict current-time claim
   receipt verification at the local deployment boundary, then invoke the one
   exact step `Deploy recovery-authorized release to GitHub
   Pages` pinned to
   `actions/deploy-pages@cd2ce8fcbc39b97be8ca5fce6e763baed58fa128`.
7. Run live postflight against the exact public deployment attestation. Request
   a third fresh custom-audience OIDC token immediately before asking the signer
   to complete or reconcile the same ledger row using the original issue
   locators, retained claim receipt, and no authorization JWS. Post-deploy the
   receipt is non-authorizing row correlation: its signature/payload and stored
   claim deadline remain mandatory even if its two-minute `exp` has passed.
   Erase the claim receipt and token after the terminal response or failure.
8. Expose only bounded terminal identifiers and the signed terminal attestation.

The recovery lane runs in a distinct `deploy-recovery` job while the historical
build/deploy path remains unchanged. The workflow must not accept a dispatch input, branch override, environment
override, database alias, artifact override, signer URL override, raw evidence,
or caller-supplied digest. Build and deploy jobs must bind the same run,
candidate, artifact ID, and artifact digest. Existing non-cancelling production
concurrency and least-privilege job permissions remain mandatory.

## Failure behavior

Every parser, endpoint, ledger operation, and verifier is fail-closed. It rejects
malformed base64url, non-canonical JSON, wrong or extra keys, unsupported
algorithms, wrong key or thumbprint, signature malleability, wrong OIDC claims,
stale protected main, stale or future times, epoch mismatch, disabled status,
stale live observations, stable-invariant or ABI drift, source, deployment
attestation, content-manifest, or artifact substitution, replay onto another
commit/run/action/target, an unsigned claim response, a used request ID or JWS,
mixed authorization modes, and any realm invariant that would open admissions
or broaden access.

No error or log returns credentials, raw evidence, JWS bytes, signatures from
rejected requests, FIDs, database rows, or upstream response details. A
dependency outage or ambiguous deployment becomes denial or reconciliation,
never implicit success.

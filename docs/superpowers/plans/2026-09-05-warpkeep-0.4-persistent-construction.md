# Warpkeep 0.4 persistent construction Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development or superpowers:executing-plans. Do not dispatch until the persistent Worker task review is resolved and this plan's interface preflight is complete.

**Goal:** Complete the persistent gather → build → benefit backend with permanent placements, one timed Builder, exact deductions and real completed-building effects.

**Architecture:** Extend the same keep, command receipts and scheduler; add only the remaining building/project private families. Shared dependency-free authority computes transitions; PTR supplies authenticated storage and atlas binding, while G002 remains explicitly closed. Reconcile project completion and Workers within one transaction and advance the aggregate revision once.

**Tech Stack:** TypeScript, SpacetimeDB2.6.1, Node22.22.3, existing numeric/placement/Worker policy, Vitest.

**Spec:** `docs/superpowers/specs/2026-09-05-warpkeep-0.4-gameplay-design.md`.

## Global Constraints

- Preserve all frozen G001 source and persistent state; no legacy population or admission changes.
- G002 remains closed for every caller; no admission design or activation.
- Every PTR player transaction including replay/read verifies current owner JWT, signed database identity, enabled retained FID/auth epoch and ready atlas/root binding.
- No client supplies acting identity, authoritative balance, completion time, route or bonuses.
- Six existing building kinds, levels1..5, one Builder, permanent placement; no queue/cancel/relocate/refund/payment/combat or new resources.
- Use checked server microseconds and integer amounts, cap1,000,000, latest128 receipts and monotonic u64 sequence/revision. Failure rolls back all writes.
- Keep SDK registrations realm-local and shared code dependency-free. No root package/lock, checked-in generated binding or final release pin changes in this task.
- No deploy/push, credentials, database reset or modifications outside task files. Final runtime journey, release preparation, live verification and Desktop handoff remain required.

Building ID is `<keepId>:building:<kind>`. One building per kind, at most six. A level-one project inserts its permanent placement with completedLevel0; only that current project's building may have level0. Upgrades preserve exact x/z/rotation and advance completedLevel by one on completion. Revision starts1 on placement and advances once per accepted project for that building; projectRevision equals that target building revision. Include building identity as well as projectRevision/due time in scheduler matching so different building projects cannot alias.

`gameplay04_building_v1`: primary buildingId, keepId index; placement microunits i64, rotationu32, completedLevelu32, revisionu64. `gameplay04_project_v1`: primary keepId, typed fields above, no opaque JSON. Both private. Exact totals PTR31/G00230. Validate all loaded records before arithmetic/output, including canonical IDs, unique kinds, bounds, layout consistency, project/building correspondence and checked timestamp interval.

The schedule table adds a lane discriminator and optional Worker/project payloads with exact mutually exclusive shapes. Total bound is five, Worker boundfour, project boundone. Preserve fresh auto-increment identities and the already-tested failed-callback cleanup recovery rules. No extra standalone scheduler table. A malformed lane or inconsistent project reference rejects before mutation.

Use the following exact realm-local SDK row shape (same private SQL name and scheduler registration):

```ts
{

  scheduledAt: t.scheduleAt(),
  keepId: t.string().index(),
  lane: t.string(), // exactly 'worker' or 'project'
```

Worker lane requires worker present/project absent; project lane requires project present/worker absent. No empty, dual, unknown, or default lane. Keep-indexed enumeration validates all rows and unique schedule IDs before splitting into WorkerStorage04 and project views; never silently filter malformed/foreign rows away. Decode scheduledAt only when its tag is Time, then enforce the same checked microsecond bounds as the core. Callback matching includes schedule ID, keep ID, lane, exact payload and due time before any reconciliation. Project callbacks additionally match the current project's building ID and project revision. The current Worker-only ABI is unreleased intermediate source, so this task changes it deliberately; it does not migrate or mutate either live database.

Stable stored graph bound is five. Atomic replacement may transiently insert a sixth row only after validating the predecessor graph and before deleting that exact predecessor, just as the Worker task permits transient replacement. No successful transaction may retain more than five rows. Test a full four-Worker plus one-project graph, replacement at that bound, and rollback between insert and predecessor deletion.

**Command semantics:**

Transaction ordering is load/authenticate → read-only input/sequence/revision preflight → non-committing project reconciliation → non-committing Worker reconciliation → command mutation → one keep/receipt commit. Pass the returned keep forward; never reload balances to replace that accumulator. Project/Worker helpers may mutate their respective rows inside the surrounding SDK transaction, but must not write keep revision or sequence. A later rejection relies on transaction rollback, which the actual adapter harness must prove. The adapter must resolve dispatch's completed levels after due project completion; resolving the target before that step would capture obsolete bonuses. Preserve exact replay as an early return before any reconciliation or target/capacity reload.

Move generic commit primitives into `commands.ts` without importing Worker runtime types:

```ts
export type CommandCommitStorage04 = KeepStorage04 & {
  updateKeep(row: KeepRow04): void;
  deleteReceipt(receiptId: string): void;
};
export function commitGameplay04Revision(
  storage: CommandCommitStorage04, keep: KeepRow04,

  canonicalFingerprint: string,

```

These are internal server-module helpers, not registered procedures or client-authority seams. Existing command-specific preflight computes and validates the same canonical fingerprint used for commit; do not accept a client fingerprint. Reuse the existing receipt pruning and overflow rules. Every command path, including dispatch/recall with construction due, must retain its preflight revision until the one final commit; tests assert one revision increment, not one per subsystem. Shared module imports must remain acyclic (commands may type-import keep; it must not runtime-import construction/reconciliation/workers).

1. Authenticate and validate current keep/atlas binding before any replay. Validate exact ordinary input keys, bounds, policy, digest and resource quote shape. Use existing sequence/key semantics. Canonical fingerprint fixed-order JSON array includes command kind `start-building`, all exact payload fields and decimal bigint strings, including all four expected resource costs and duration.
2. Retained exact replay returns its original seq/revision even after completion; no deductions or project recreation. Conflicting/pruned/gap sequence rejects. Fresh expectedRevision compares with loaded keep before reconciliation; stale commands perform no writes.
3. Reconcile due construction first, then due Workers in ordinal order, inside the same transaction without separately incrementing aggregate revision. A new dispatch after a project completes captures completed levels from actual validated building rows, replacing the existing all-zero adapter. Ongoing expeditions retain captured yield/travel.
4. Require no remaining active project after reconciliation. For a new kind require targetLevel1 and run evaluatePlacement04 against every existing placement, including any construction footprint. For upgrade require exact persisted transform and targetLevel==completedLevel+1<=5. Never re-place a building under upgrade semantics.
5. Compute cost through buildingCost04 and duration through buildingDuration04 using actual completed Cathedral level. Require exact expectedCost/expectedDurationMicros and current fixed layout digest; reject mismatches, never silently rebind quotes. Check every balance before any deduction; subtract all four atomically.
6. Persist placement/revision and one project, schedule its future completion, record receipt and last sequence, prune latest128, advance aggregate revision exactly once for the whole accepted command. Reject timestamp, building revision, account revision or sequence overflow rather than wrap.
7. Completion advances only the target completedLevel, clears project and exact wakeup, and does not deduct again or grant unrelated resources. Repeat/stale callbacks cannot advance twice or clear a replacement. Missing wakeup can be recreated/overdue completion reconciled only after full authenticated state validation. Disabled owner cannot complete/repair.
8. Authenticated read and scheduler use reconcileGameplay04, advancing revision once if any project/Worker storage changed and consuming no command sequence. Normal clock passage alone does not write. Project completion before a Worker return does not change that Worker's captured yield.

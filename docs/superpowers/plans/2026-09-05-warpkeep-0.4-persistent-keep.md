# Warpkeep 0.4 persistent keep Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Register and test real owner-authenticated PTR keep initialization and private state reads, with durable retry protection and the corresponding explicitly closed G002 boundary.

**Architecture:** A dependency-free transaction authority operates on narrow typed storage methods; module-local adapters supply actual database tables, fresh owner authorization and verified atlas bindings. SDK descriptors and procedure registration stay inside each realm module. This is the first persistent vertical slice, not a replacement for the remaining gathering, construction, scheduler, client, release and live acceptance work.

**Tech Stack:** TypeScript; module-local SpacetimeDB 2.6.1; existing Vitest; pinned local Node 22.22.3.

**Spec:** `docs/superpowers/specs/2026-09-05-warpkeep-0.4-gameplay-design.md`.

## Global Constraints

- Leave every frozen G001 source projection and persistent row intact.
- G002 player commands always reject while closed; neither an admin role nor deployment opens play.
- No request supplies the acting FID or authoritative keep.
- PTR commands require current signed database identity, enabled retained owner, matching FID/auth epoch and fresh owner JWT on every transaction, including replay and reads.
- Keep all legacy empty-population guards; new private state never populates legacy resourceAccount/worker/castle/player/admission descriptors.
- Shared `spacetimedb/gameplay04` runtime code stays dependency-free; instantiate SDK descriptors inside each realm module.
- Balances cap at 1,000,000 per resource. No browser clock, client balance, client route or yield is authority.
- Four Workers, latest 128 receipts, monotonic u64 command sequence, exact expected aggregate revision. Failed transactions consume no sequence.
- Request keys are `g04:<canonical-decimal-sequence>:<32-lowercase-hex-nonce>` and must match the supplied sequence.
- No root dependency installation: repository node_modules is an existing junction. Do not change frozen package locks, install into that junction, deploy, push, reset data or read credentials for this task.
- Preserve unrelated dirty files. Stage only this task's exact files.

## Delivery boundary and sequence

This task installs three of the final seven private families: keep, Worker slots and receipt. Thus its intermediate schema totals are PTR27/G00226. Later gathering adds reservation/schedule; construction adds building/project, reaching the spec's final PTR31/G00230. No intermediate graph is a releasable 0.4 module. This ordering avoids empty placeholder reducers and invented scheduler callbacks while giving subsequent mechanics actual persistent account/sequence ownership.

The next integration must extend these same records, not introduce a second account or retry store. Before generating release pins, all seven families and full gameplay must be present. Initialization and read are independently testable now; they are not evidence that gather/build is delivered.

**Interfaces and persistent shapes:**

Use these dependency-free types in `keep.ts`; SDK tables mirror the scalar fields. `ownerFid` is private, never returned by the new state response. Keep IDs are derived by the adapter as `g04:<databaseIdentity>:<ownerFid>` using canonical lowercase database hex and decimal FID.

```ts
export type KeepBinding04 = Readonly<{
  keepId: string; databaseIdentity: string; ownerFid: bigint;
  atlasId: string; atlasRevision: bigint; anchorCellKey: string;
}>;
export type KeepRow04 = KeepBinding04 & Readonly<{
  policyVersion: string; revision: bigint; lastAcceptedSequence: bigint;
  food: bigint; wood: bigint; stone: bigint; gold: bigint;
  createdAtMicros: bigint;
}>;
export type WorkerSlot04 = Readonly<{
  workerId: string; keepId: string; ordinal: number;
  assignmentRevision: bigint;
}>;
export type ReceiptRow04 = Readonly<{
  receiptId: string; keepId: string; sequence: bigint;
  requestKey: string; fingerprint: string; resultRevision: bigint;
}>;
export type InitializeKeepInput04 = Readonly<{
  sequence: bigint; requestKey: string; expectedRevision: bigint;
  policyVersion: string;
}>;
export type InitializeKeepResult04 = Readonly<{
  sequence: bigint; revision: bigint;
}>;
export interface KeepStorage04 {
  findKeep(keepId: string): KeepRow04 | null;
  workers(keepId: string): Iterable<WorkerSlot04>;
  receipts(keepId: string): Iterable<ReceiptRow04>;
  insertKeep(row: KeepRow04): void;
  insertWorker(row: WorkerSlot04): void;
  insertReceipt(row: ReceiptRow04): void;
}
export function initializeKeep04(
  storage: KeepStorage04, binding: KeepBinding04, nowMicros: bigint,
  input: InitializeKeepInput04,
): InitializeKeepResult04;
export function readKeep04(
  storage: KeepStorage04, binding: KeepBinding04,
): Readonly<{ keep: KeepRow04; workers: readonly WorkerSlot04[] }>;
```

Worker ID is `<keepId>:worker:<ordinal>` for ordinals 0..3. Receipt ID is `<keepId>:receipt:<sequence>`. Table primary keys: keepId, workerId and receiptId respectively. Worker and receipt keepId fields are indexed. There is no autoincrement, public table, public owner lookup or direct client table subscription. Worker slots are retained rows; the gathering task adds their actual assignment payload before release rather than storing opaque unvalidated JSON now.

Wire functions are procedures named exactly `initialize_gameplay04_keep_v1` and `get_gameplay04_keep_v1`, exported as `initializeGameplay04KeepV1` and `getGameplay04KeepV1`. Initialize takes the four input fields above and returns `{sequence, revision}`. Read takes no arguments and returns `{policyVersion, revision, lastAcceptedSequence, food, wood, stone, gold, workers}` where workers contain only `{ordinal, assignmentRevision}`. No owner FID, keep ID, JWT, database credential or private receipt content appears in this response. These shapes are intentional first-slice contracts, extended before final generated bindings for journeys/buildings.

**Transaction and error behavior:**

1. Production PTR procedure enters `ctx.withTx`, calls `requirePtrOwner(tx)`, then `requirePtrReadyAtlas(tx)`. Build binding from `tx.databaseIdentity.toHexString()`, returned `claims.fid`, validated atlas release/import epoch and root cell. Use `tx.timestamp.microsSinceUnixEpoch` only. Never expose an injectable authorization callback through the procedure wire.
2. Validate exact ordinary record input fields and types, u64 bounds, policy equality and request-key grammar before writes. Bound strings before regex/serialization. Keep existing pure modules' controlled errors; map this authority's errors to stable `SenderError` codes without echoing input/session content.
3. Validate binding: canonical database hex length64, positive u64 owner FID, positive u64 atlasRevision, nonempty bounded atlas/cell keys; keepId must exactly derive from database/FID. Timestamp must be 0..i64max.
4. For no keep, require sequence1 and expectedRevision0. Reject orphan Worker/receipt rows (bounded scans terminate at fifth Worker/129th receipt). Insert keep with policy constant, revision1, lastAcceptedSequence1, all balances0, server creation time; four idle slots with assignmentRevision0; one receipt. All inserts occur in the same real transaction.
5. For existing keep, validate exact database/FID/atlas/revision/anchor/policy binding and stored integer bounds before replay. A changed atlas binding fails `GAMEPLAY04_BINDING_MISMATCH`; it never reseeds. Validate exactly four unique correctly keyed slots in ordinal order. Validate bounded receipt rows and canonical identities/sequences; malformed stored state fails closed.
6. Retained sequence and exact request key/fingerprint returns the original sequence/resultRevision without writes, even after aggregate revision changes. Changed fingerprint/key rejects `GAMEPLAY04_RECEIPT_CONFLICT`. Missing sequence <=lastAccepted rejects `GAMEPLAY04_RECEIPT_EXPIRED`. A new initialization against an existing keep rejects `GAMEPLAY04_ALREADY_INITIALIZED` (no sequence consumption). Sequence gaps reject `GAMEPLAY04_SEQUENCE_INVALID`.
7. Canonical fingerprint is `JSON.stringify(['initialize', sequence.toString(), requestKey, expectedRevision.toString(), policyVersion])`, stored as exact bounded canonical text rather than a collision-prone custom hash. This command has no layout/placement payload; future building commands must include their layout digest. Exclude session expiry so normal same-owner renewal can replay.
8. Read repeats current owner/atlas authorization, validates binding and stored rows, and returns immutable sorted copies. Missing keep is `GAMEPLAY04_NOT_INITIALIZED`; no implicit initialize. Reads here have no due work and perform no writes. Later integration adds bounded reconciliation in this same transactional entry point.
9. G002 procedures enter the actual module transaction and throw `SenderError('GENESIS002_GAMEPLAY_CLOSED')` before touching gameplay storage, for all callers including admin. Preserve admin-only connection. `requireGenesis002PopulationEmpty` additionally checks the three new table counts and rejects any nonzero row. Do not alter the existing public policy snapshot type just to pretend old tests cover these counts; add direct count tests.

```ts
test('initialization is persistent and retry has no second effect', () => {
  const first = tx(() => initializeKeep04(store, binding, 100n, input));
  const before = snapshot();
  const retry = tx(() => initializeKeep04(store, binding, 200n, input));
  assert.deepEqual(first, { sequence: 1n, revision: 1n });
  assert.deepEqual(retry, first);
  assert.deepEqual(snapshot(), before);
  const state = readKeep04(store, binding);
  assert.deepEqual(state.workers.map(w => w.ordinal), [0, 1, 2, 3]);
  assert.equal(state.keep.food + state.keep.wood + state.keep.stone + state.keep.gold, 0n);
});
```

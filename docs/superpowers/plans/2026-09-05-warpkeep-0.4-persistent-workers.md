# Warpkeep 0.4 persistent Workers Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Execute real owner-only PTR dispatch, recall and once-only returned-resource credit using verified isolated atlas capacity, persistent assignments and server scheduling.

**Architecture:** Extend the accepted keep/Worker/receipt families; do not introduce another account or retry store. Share dependency-free transactional Worker authority and use realm-local SDK storage/auth/scheduler adapters. PTR resolves real atlas facts; G002 registers the same closed command surface without admitting players. This is the Worker integration, not full construction/client/release acceptance.

**Tech Stack:** TypeScript, pinned SpacetimeDB2.6.1, pinned Node22.22.3, Vitest, existing pure policy and Journey04.

**Spec:** `docs/superpowers/specs/2026-09-05-warpkeep-0.4-gameplay-design.md`.

## Global Constraints

- Leave every frozen G001 source projection and persistent row intact.
- G002 player commands always reject while closed; neither an admin role nor deployment opens play.
- No request supplies the acting FID or authoritative keep.
- Every PTR player transaction, including replay/read, requires fresh owner JWT, matching signed database identity, retained enabled owner FID/auth epoch and verified ready atlas binding.
- Keep all legacy empty-population guards and legacy imported resource flags inactive/unassigned. No G001 activation or admission path.
- Four Workers, latest128 command receipts, u64 monotonic command sequence, exact aggregate revision, server microsecond time. Failed transactions consume no sequence and rollback reconciliation.
- Balance cap1,000,000 per resource; credit only at return completion and report overflow. Reconcile in Worker ordinal order.
- SDK2.6.1 descriptors/registration remain module-local; shared runtime stays dependency-free. Do not alter root packages/locks or install into the root node_modules junction.
- Preserve frozen production source, unrelated dirty state, current release pins and checked-in bindings. No deploy, push, credential access or data reset for this implementation task.

`Assignment04` and `ReturnOutcome04` live in `workerState.ts` and are re-exported from `workers.ts`. Every keep read/replay validates any present assignment/outcome before returning; full reservation/schedule graph validation belongs to Worker authority. Validate ordinal type/range before sorting. Store the complete bounded private route as the route commitment, not an unverified client digest; validate it and its journey edge count together.

The resolved target is an internal production adapter value, never procedure input. Export the following from `workers.ts` (using the sequence/replay helpers in commands.ts):

```ts
export function preflightWorkerCommand04(storage: WorkerStorage04,
  binding: KeepBinding04, now: bigint,
  command: Readonly<{kind: 'dispatch'; input: DispatchWorkerInput04}>
    | Readonly<{kind: 'recall'; input: RecallWorkerInput04}>):
  Readonly<{kind: 'replay'; result: WorkerCommandResult04}>
    | Readonly<{kind: 'fresh'; revision: bigint}>;
```

This validates exact command shape and loaded account/receipts without writes or resource loading. The production dispatcher invokes it after current owner/atlas authorization and before resource resolution; the shared mutator repeats the same validation rather than trusting a boolean authorization flag. A replay must succeed after its original node is occupied by a later assignment, provided current owner/atlas binding remains valid. Do not expose storage, target facts or callbacks through the network wire. commands.ts must not runtime-import keep.ts; move shared error/receipt primitives there and re-export existing public keep names if needed, preserving existing error codes and fingerprint bytes.

Use one private reconciliation helper that applies bounded Worker/reservation/schedule/balance changes and returns the updated keep plus a changed flag, without advancing the aggregate revision. The public reconcileWorkers04 wrapper commits one revision only when changed; fresh dispatch/recall combine that helper and the command, then commit exactly one revision. Never call the public revision-advancing wrapper from a command and then increment again. Schedule replacement may transiently insert a fifth row before deleting its predecessor inside the atomic transaction; enforce the four-row bound on input and committed output, not on that transient insertion.

**Command and reconciliation algorithm:**

1. Owner and ready-atlas checks stay first, inside the actual transaction. Compare current database/atlas/root against persisted binding. Client expectedAtlasRevision must equal the stored/current revision. Reject malformed exact input keys, invalid u64/integer ordinals0..3, unknown resource, unsupported duration and bounded strings before resource work or writes.
2. Shared commands use the existing keep sequence. Retained exact key/fingerprint replays original result; conflicting replay rejects. Pruned sequence<=lastAccepted rejects; next must be last+1. New-command expectedRevision equals the loaded aggregate revision. Reject revision/sequence overflow, never wrap. Canonical fingerprints include command kind, all exact input fields in fixed order, canonical decimal bigints, policy and atlas expectations; no secrets/session timestamps. Preserve original initialization fingerprint bytes.
3. Before a fresh command, reconcile up to four Workers in ordinal order within the same transaction. Delay the aggregate revision write so reconciliation plus accepted command advances it exactly once. An authenticated read or scheduler reconciliation advances only when stored state actually changes and consumes no command sequence. Any later command error rolls back reconciliation, reservations, schedules, balances and receipt together.
4. Dispatch requires selected Worker idle after reconciliation. Resolve one bounded32-node location index group from actual PTR atlas, sort by nodeOrdinal, require contiguous ordinals and release ordinals, unique canonical node IDs, consistent atlas/location/cell/component/region/resource/policy/tier and inactive/unassigned legacy shape. Validate the actual destination cell and resource group against the ready atlas. Never trust client window/node count or activate legacy nodes.
5. Resolve full route once via extracted existing verified parent-tree algorithm, starting at persisted root anchor, ending at actual resource cell. Validate returned path1..8193 points, i32 coordinates, adjacency and endpoints; zero edges only for the real origin resource cell. Avoid rebuilding the entire path once per128-cell page. Resource fact loader provides nodes in validated ordinal order; pick first node with no private reservation. Full/foreign reservation conflict rejects without writes.
6. Increment the retained Worker's assignmentRevision exactly once for a new expedition (u64 overflow rejects), capture server time and completed-building effects through dispatchJourney04 with route.length-1. Persist assignment and node reservation together. Schedule the first future due phase from observeJourney04; zero-distance arrival can already be gathering, so never spin on a past/no-op due timestamp.
7. Recall uses recallJourney04, including exact partial-edge return time and completed quanta. A returning Worker retains its return plan; idle recall is an accepted no-op command with normal sequence/receipt semantics. Replace a changed assignment's current wakeup with a fresh schedule ID even though expedition assignmentRevision is unchanged; matching the callback must include schedule identity and due time, not only assignmentRevision.
8. Reconciliation derives current phase from persisted Journey04 and now. On completion verify exact reservation owner/Worker/assignment revision, creditResource04 into the matching account, retain explicit lastReturn(earned/credited/overflow/recorded returnsAt), release reservation, clear assignment and its schedules atomically. Repeated reads/callbacks never credit twice. LastReturn persists across next dispatch until replaced by next return; it is bounded to one per Worker.
9. Pending phase transitions need only update a wakeup when its due timestamp changes; do not write every read or increment revision for the wall clock alone. Require exactly one matching future wakeup per active assignment after reconciliation, no reservation for idle Worker, at most four claims/schedules and exact one-to-one ownership. Malformed state fails closed. The retained Minor must be fixed here: validate Worker ordinal scalar/type/range before sorting, yielding controlled state errors.
10. On accepted mutation, increment aggregate revision once, persist lastAcceptedSequence and receipt, prune oldest sequences to latest128. No unbounded receipts scan: permit129 only during insert/prune within one transaction, retain128 on exit. Failed commands do not consume sequence. Returned result is the committed seq/revision; authoritative current Worker state is read separately.

**Scheduler authority and lifecycle:**

Use reducer context sender==databaseIdentity and connectionId==null, plus actual table-schedule registration. Do not use senderAuth.isInternal or an expired player JWT. Resolve the stored keep by the scheduled keepId; confirm its database binding, ready atlas/root and exactly one retained enabled owner matching its FID before any work. Compare callback argument with the current stored schedule ID/Worker/revision/Time due value, and current assignment. Missing/stale callback is a no-op and cannot delete a newer row. Future-due callback is no-op. Wrong module/client caller rejects.

A disabled owner authorizes no settlement or new wakeup; preserve resources/assignment/reservation and perform no gameplay writes. Suspension is permanent, not an invitation to implement unsuspend. G002 internal callbacks always reject closed gameplay and create no state.

One-shot reducer rows are removed after execution according to current official docs. Always insert a new auto-increment schedule identity for the successor phase, and delete only the matching old row. Real pinned-runtime lifecycle testing remains required before release; local SDK schema/callback tests alone do not prove runtime auto-deletion ordering. Do not fake that result or change production auth to manufacture it.

Pinned v2.6.1 scheduler source additionally removes the one-shot row after a failed/trapped callback. Treat a missing wakeup for an otherwise fully valid active assignment and exact retained reservation as recoverable delivery loss, not missing financial authority. Authenticated read/fresh command reconciliation may recreate the next future wakeup or settle an already-complete journey once from its persisted timing and claim. Validate the complete keep/assignment/route/reservation graph first; conflicting, duplicate or malformed existing schedules still reject. An absent callback row itself remains a no-op: only normal authenticated reconciliation repairs this case, never an unauthenticated stale callback. Disabled owners cannot repair or settle. Test callback rollback followed by engine cleanup (remove only the due schedule in the harness), then read before return recreates one wakeup, and read after return credits once. This preserves spec-required recovery from delayed/failed delivery without treating schedule presence as resource ownership.

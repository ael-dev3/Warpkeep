# Warpkeep 0.4.0 Protected Release Operations Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use
> superpowers:executing-plans for these sequential production operations. Use
> superpowers:verification-before-completion before every live-success claim.

**Goal:** Starting from the inert protected-main preparation merge, create
receipt-proven sealed Genesis 002 and owner-only PTR, activate the exact
three-file 0.4.0 successor, deploy it, tag it, and finish with zero open PRs.

**Architecture:** The fixed production workflow and dispatcher operate from
receipt-derived state on the repository-exclusive macOS ARM64 runner. G002 and
PTR publication do not depend on the auth bridge. PTR publication, ownerless
atlas import, and configured-owner provisioning are separate receipt lanes.
Time-sensitive G001 evidence runs last, immediately before activation
generation. Only the privacy-safe generated binding crosses into Git.

**Preparation Plan:**
`docs/superpowers/plans/2026-08-30-warpkeep-0.4.0-preparation.md`

**Runbook:** `docs/operations/genesis-002-sealed-launch.md`

This operations plan is runnable only after preparation Task 7. Task 6B changes
two current raw closure members without refreeze and begins the intentional
stale-pin interval. Task 6C's surface intersects 21 current raw members total,
including those same two; it adds 19 newly distinct members, so the union
through Task 6C is 21. Task 6C continues the interval, and Tasks 6D and 6E
continue it. Neither the protected prepared workflow nor
any sealed-realms/live production workflow may execute from a Task 6B-6E
intermediate commit. Their closure-dependent cases must fail closed; focused
task-specific source/module/static review is not a full-green workflow claim.
Task 7 alone atomically refreezes every closure/workflow/downstream pin, reaches
a completely green first run, and proves a zero-diff second run before these
operations become executable.

## Immutable authority

Source mode `S` exists only when checkout `HEAD`, protected remote `main`, the
workflow input commit, the inert preparation binding, and the successful
Verify SHA are identical. All 20 operations below are permitted in `S`:

```text

```

No CLI postflight, bridge deployment/reconciliation, G001 launch cleanup,
admitted-player census, public artifact verifier, or post-activation read is a
21st operation. CLI postflight and admitted-player collection are internal to
the corresponding existing operation; launch cleanup is internally owned by
`g001-policy-observe`; bridge work is the existing protected bridge workflow;
artifact verification is a non-dispatch verifier; and post-activation reads
reuse the four names allowed in `A`.

Source mode `A` requires the exact activated binding, exactly one parent equal
to `S`, a raw NUL-safe diff of exactly these regular mode-`100644` files, a
successful Verify at `A`, and binding/history verification:

```text
config/releases/0.4.0-sealed-launch.json
package-lock.json
package.json
```

Outside `S`, only `A` is permitted, and it permits only `preflight`,
`g001-current-state`, `g002-live-inspect`, and `ptr-live-inspect`. After `A`,
no publish, import, provision, G001 policy-observe, census, suspension, or
activation-generation operation may run.

The workflow has exact permissions `actions: read` and `contents: read`, exact
20-choice input, fixed runner labels `[self-hosted, macOS, ARM64,
warpkeep-production-admin, warpkeep-repository-exclusive]`, protected
environment `notification-bridge-prepared`, shared non-cancelling concurrency
with every state-touching workflow, and one bounded privacy-safe result line
with exact prefix `WARPKEEP_OPERATION_RESULT `.
Production performs no npm, pnpm, tsx, root-node-modules, bootstrap download,
or package installation. Fixed signed Node 22 runs only the builtins dispatcher
and authenticated checked-in lane bundles. It requires
`globalThis.WebSocket` before opening an admin secret or starting network work.

All private applicant/admitted-player evidence, owner FID/auth epoch, census
counts/raw digests, CLI configuration, tokens, receipt bodies, and absolute
private paths remain in the three existing subsystem-owned account-home roots.
The dispatcher never creates or repairs those roots. It creates only
`sealed-realms-v1` children and canonical bounded no-clobber owner-owned regular
single-link mode-`0600` files, followed by directory fsync.

Every mutation confirmation is consumed before authority is released. An
ambiguous result writes reconciliation state that can never reactivate that
confirmation. The corresponding existing inspect operation alone may prove
adoption, resume, or no effect; a possibly submitted publication or reducer is
never replayed.

Before either publication callback is released, the dispatcher durably writes
the Task 6C pure marker profile
`warpkeep-sealed-realms-publication-possibly-submitted-v1`. Its exact ordered
fields are `schemaVersion`, `profile`, `lane`, `sourceCommit`, `databaseUri`,
`alias`, `moduleIdentity`, `release`, `artifactDigest`, `toolchainDigest`,
`publishPlanDigest`, `confirmationDigest`, `attemptNonce`, `markedAt`, and
`submissionState=possibly-submitted`. Task 6C owns pure canonical constructor/
parser/digest and marker-to-receipt reconciliation ABIs. Publish inspect binds
its exact plan and confirmation, and the dispatcher persists the marker no-
clobber plus fsync before returning the confirmation or permitting apply.
Task 6D owns that persistence, restart
reconciliation, adoption/no-effect records, and no-replay authority.

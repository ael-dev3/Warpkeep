# Warpkeep 0.4.0 Recovery Release and Local Package Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development task-by-task. Every behavior change starts with a failing test and receives a fresh requirements review.

**Goal:** Integrate the approved recovery authorization into Warpkeep's release verifier and Pages workflow, then produce a clean, verified, non-secret `Warpkeep-0.4.0` package on the Windows Desktop without performing any remote mutation.

**Architecture:** Schema 1 remains the unchanged historical-receipt path. Schema 2 is a separately parsed recovery path whose historical G001 receipt slots stay null, whose commitment graph is acyclic, and whose runtime authority is a private short-lived JWS plus durable claim. A distinct hosted `deploy-recovery` Pages job consumes that authority. The Desktop deliverable is generated from committed source and a fresh build, records that production was not deployed, and points to host-side CLI login state without copying credentials.

**Tech Stack:** Node 22, root npm 10, recovery/auth-bridge pnpm 11.7.0, TypeScript 7, Vitest 4, Vite 8, GitHub Actions YAML, PowerShell 7, SHA-256.

**Specs:**

- `docs/superpowers/specs/2026-09-03-warpkeep-0.4.0-recovery-authorization.md`
- `docs/superpowers/plans/2026-09-03-warpkeep-0.4.0-recovery-service.md`

## Global constraints

- Never change schema-1 key order, canonical bytes, commitment formula, parser acceptance, or historical activation behavior.
- Schema 2 uses `authorizationMode: recovery-authorization-v1`; the historical G001 receipt digest and commitment are exactly null.
- Compute each schema-2 non-historical receipt commitment with `recoveryAuthorizationCoreSha256` forced null. Compute the core last over the complete schema-2 binding with only its own slot null.
- The preparation commit/tree/closure are static. The activation candidate is its single child with exactly `config/releases/0.4.0-sealed-launch.json`, `package.json`, and `package-lock.json` changed.
- The recovery job is GitHub-hosted, uses the `github-pages` environment, has no dispatch inputs, and cannot reach `actions/deploy-pages` until strict JWS, claim receipt, and twice-fresh signed status checks pass.
- Do not provision, deploy, upload a secret, dispatch a workflow, push, merge, or modify remote data in this plan. After Task 6, this plan pauses at an explicit external disabled-deployment/readback interlock; a separately authorized deployment session must satisfy it before local Task 7 may resume.
- Do not copy `.git`, dependency directories, `.env*`, `.dev.vars`, Cloudflare `.enc` profiles, SpacetimeDB `cli.toml`, tokens, JWK private material, FIDs, private/generated receipt bodies, remote exports, browser profiles, or logs into the Desktop package. Receipt-related source filenames and non-secret test fixtures remain ordinary committed source.
- The Desktop folder is a local 0.4.0 deliverable, not evidence of production deployment. Its manifest must say `productionDeployed: false`.

**Execution order:** release Task 0 -> recovery-service plan Tasks 1-8 -> release Tasks 1-5 -> release Task 6 -> external disabled-deployment/readback interlock -> release Task 7 -> release Task 8 -> release Task 9. This explicit cross-plan order is authoritative. If the external interlock has not produced authenticated readback evidence, stop after Task 6 and do not label a preparation-parent package as the 0.4.0 activation candidate.

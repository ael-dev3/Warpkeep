## Continuous publication contract

- Review and commit the exact durable work authored for this project, including
  new source files, then push and compare the actual remote SHA. Combine a
  change with its tests and notes rather than issuing status-only follow-ups.
- During longer changes, publish bounded unfinished checkpoints before switching
  work items. Record known failures and checks still pending; do not defer the
  backup until the whole feature is complete or the periodic check runs. A
  checkpoint ends with a verified live GitHub SHA or an exact publication blocker.
- At handoff, inspect staged/unstaged/untracked paths and outgoing history.
  Publish agent-authored unfinished source with its known limitations; incomplete
  release acceptance is not a reason to leave development unbacked up.
- Exclude credentials, private receipts, caches, logs, dependency trees and
  disposable builds. Valid generated source is published as its complete checked
  family, never as a partial or still-mutating output set.
- Coordinate one commit/push owner with active agents. Preserve unrelated user
  work. If scanning, remote access, conflicting advancement or active generation
  prevents publication, record the exact retained work and blocker and resume
  automatically once it clears; never force a push or bypass the check.
- A native preparation/check owns an immutable input. Keep that operating
  checkout pinned while its real process runs; after completion, synchronize
  the clean idle checkout to the published head. Record the input separately
  from the latest documentation/implementation head until then.
- Apply the same process to changed related repositories using their own
  reviewed paths and remotes; do not put asset-repository work or private
  infrastructure state into the wrong repository.

## Fetch and inspect the outgoing history

Use the existing authorized GitHub authentication. The previous session-specific
network denial was superseded by successful authenticated reads on September 7;
retry the required operation and report its actual result if access fails.
Never print a token or copy credential-store contents.

After resolving the authorized branch as described above, this PowerShell
sequence records an existing remote branch's current base. It uses the inspected
Windows publication remote; related repositories use their own verified remote.

```powershell
$wkRemote = 'origin' # Inspected remote for C:/Temp/warpkeep-0.4-next.
$wkBranch = (git branch --show-current).Trim()
if ($LASTEXITCODE -ne 0 -or !$wkBranch) {
    throw 'Resolve the authorized development branch before publication.'
}
$wkRef = "refs/heads/$wkBranch"
$wkPushUrl = git remote get-url --push $wkRemote
if ($LASTEXITCODE -ne 0 -or $wkPushUrl.Trim() -ne 'https://github.com/ael-dev3/Warpkeep.git') {
    throw 'Reconcile the actual publication target before continuing.'
}
git fetch --no-tags $wkRemote $wkRef
if ($LASTEXITCODE -ne 0) { throw 'Fetch failed; do not infer remote state.' }
$wkRemoteBefore = (git rev-parse --verify 'FETCH_HEAD^{commit}').Trim()
if ($LASTEXITCODE -ne 0) { throw 'Could not resolve the fetched branch.' }
git log --oneline "$wkRemoteBefore..HEAD"
git diff --stat "$wkRemoteBefore..HEAD"
git merge-base --is-ancestor $wkRemoteBefore HEAD
if ($LASTEXITCODE -ne 0) { throw 'Remote history needs review and reconciliation before pushing.' }
```

Inspect every outgoing commit, not only the latest commit or current worktree
diff. New local commits can contain earlier unfinished work and earlier secrets.
For an authorized new branch, first verify that the exact remote ref is absent
with a successful remote query; distinguish absence from an authentication or
network failure. Use its verified, already-published base as `$wkRemoteBefore`,
scan every outgoing commit from that base, then publish the new ref explicitly.
Do not reuse an old `FETCH_HEAD` after a failed fetch or recreate a retired branch.
If the remote advanced independently, fetch and reconcile its real changes in
an isolated checkout when needed. Do not force-push, overwrite a collaborator's
ref, or assume automatic pull/rebase is harmless to shared work.
When a maintained checkout is clean, idle and strictly behind its verified
authorized branch, use a fast-forward-only update and verify local/live equality.
This includes the detached WSL operating checkout after a real preparation/check
process releases it. Preserve dirty, ahead or diverged work for its owning agent;
resolve branch transitions before moving a checkout.

## Review, verify and form the checkpoint

1. Review the exact scoped change and its callers, generated outputs and public
   evidence. Review new files before selecting them. Never hand-edit generated
   closure counts or source hashes to hide an integration failure.
2. Run checks appropriate to the change and record source, toolchain, selected
   tests, exit codes and limitations. Documentation needs link/source checks and
   relevant repository contracts. Gameplay, auth, module, asset and release-script
   changes need their own checks. Existing failing release integration does not
   block an honestly labeled development backup, but remains a release blocker.
3. Use the pinned tools. PATH Node may be outside the required major. The retained
   Windows executable is `C:/Users/heyas/Documents/Codex/2026-08-11/pl/Warpkeep-0.4.0-worktree/.git/ci-node-22.22.3/node.exe`.
   Inspect dependency ownership: some old worktrees share a `node_modules`
   junction, while the current active checkout has an independent directory.
   Do not install into a shared junction. Explicit app and Vite project
   typechecks are documented in the development workflow.
4. Coordinate the index, stage only the agreed exact paths, then inspect
   `git diff --cached --stat`, the complete staged diff and
   `git diff --cached --check`. Do not commit another agent's staged changes.
   Separate implementation, generated outputs and documentation when that helps
   review; do not split a required atomic generated family into an invalid state.
5. Commit the reviewed checkpoint. Record its full SHA and confirm the commit
   contains the intended files. Keep unrelated dirty and untracked material in
   place. A clean commit can be published from a dirty checkout if its exact
   contents and ancestry have been reviewed; a dirty working directory itself
   is not what Git pushes.

Scan the **entire outgoing committed range** before any push, using the reviewed
pinned Gitleaks 8.30.1 executable and `.gitleaks.toml`. For example, after setting
`$wkReviewedSha` to the full reviewed commit SHA and selecting that executable:

```powershell
git rev-parse --verify "${wkRemoteBefore}^{commit}" > $null
if ($LASTEXITCODE -ne 0) { throw 'Fetched starting commit is unavailable.' }
git rev-parse --verify "${wkReviewedSha}^{commit}" > $null
if ($LASTEXITCODE -ne 0) { throw 'Reviewed ending commit is unavailable.' }
gitleaks git --config .gitleaks.toml --redact --no-banner "--log-opts=$wkRemoteBefore..$wkReviewedSha --diff-merges=first-parent" .
if ($LASTEXITCODE -ne 0) { throw 'Resolve the exact scan result before publication.' }
```

Inspect the scanner's Git diagnostics and scanned-commit count as well as its
exit code. A missing remote-tracking ref can produce a Git error and a zero-commit
“no leaks” result. Use the resolved fetched SHA above; zero scanned commits is
not acceptable evidence for a nonempty outgoing range.

Include merge diffs in the outgoing scan. Git's default log can omit a merge
commit's patch, leaving conflict resolutions or notes first introduced in that
commit unscanned. `--diff-merges=first-parent` exposes that content while the
complete outgoing range still includes commits from every newly merged parent.
Do not add `--first-parent`, which would hide the other new history. A scan that
omits the merge's patch does not establish full outgoing coverage.

Do not assume a nonzero scan means a real secret, or that test data makes every
finding harmless. Inspect findings privately and redact reports. Narrow,
reviewed exceptions must identify the actual synthetic/public fixture and scope;
do not disable a rule globally or skip a failed scanner. A launch/network/tool
failure is an unexecuted check, not a clean scan. If a real secret is in outgoing
history, stop publication of that history and remove/rotate it through the
appropriate process; never rewrite an already-shared branch without coordination.
A later deletion does not remove a secret from earlier outgoing commits. Retain
the affected work privately and report that specific blocker. If repairing it
requires rewriting history that the current task does not authorize, obtain that
authorization before repair; the periodic sync check must not silently bypass its
no-history-rewrite boundary or repeatedly retry the contaminated range.

## Push one reviewed SHA, then verify the result

Recheck that the reviewed commit still contains the intended work and that no
concurrent index/commit change has silently replaced it. Push the explicit SHA
with an explicit non-forced refspec:

```powershell
if ($wkReviewedSha -cnotmatch '^[0-9a-f]{40}$') {
    throw 'Set the full reviewed commit SHA before publication.'
}
git merge-base --is-ancestor $wkRemoteBefore $wkReviewedSha
if ($LASTEXITCODE -ne 0) { throw 'Reviewed checkpoint does not include the fetched remote history.' }
git push $wkRemote "${wkReviewedSha}:$wkRef"
if ($LASTEXITCODE -ne 0) { throw 'Push did not succeed; inspect the exact failure.' }
$wkRemoteLines = @(git ls-remote --exit-code $wkRemote $wkRef)
if ($LASTEXITCODE -ne 0 -or $wkRemoteLines.Count -ne 1) {
    throw 'Remote verification failed; publication outcome needs reconciliation.'
}
$wkRemoteParts = $wkRemoteLines[0] -split '\s+'
if ($wkRemoteParts.Count -ne 2 -or $wkRemoteParts[0] -cne $wkReviewedSha -or $wkRemoteParts[1] -cne $wkRef) {
    throw 'Remote is not the exact reviewed checkpoint; inspect concurrent advancement.'
}
gh pr view $wkBranch --repo ael-dev3/Warpkeep --json url,isDraft,headRefName,headRefOid,statusCheckRollup
if ($LASTEXITCODE -ne 0) { throw 'Branch pushed; PR/check status remains unverified.' }
```

A rejected push requires fresh inspection, not a force retry. A timeout or lost
response is ambiguous: read the remote ref before retrying, because the push may
already have succeeded. If another authorized commit advanced the branch after
ours, distinguish verified ancestry from exact equality and report both SHAs.
Do not rewrite that advancement to recover an earlier exact-match claim.

Resolve the active PR for the verified development branch and read its actual
base, draft, merge and check state. Create a PR through the normal authorized
workflow if this is a new branch; absence of a PR does not undo a verified push.
A queued run, partial success or earlier-head result is
not a pass for the new checkpoint. Recheck workflow triggers whenever workflows
change.
The inspected configuration runs Verify/CodeQL for PRs and limits automatic Pages

operations require explicit dispatch. This boundary must remain true for the

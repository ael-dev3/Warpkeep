# 0.4.0 recovery bootstrap

`scripts/prepare-0.4.0-recovery-bootstrap.mjs` prepares and verifies the
owner-private material for the `recovery-authorization-v1` path. It is a local
filesystem command only. It does not contact Cloudflare, GitHub, SpacetimeDB,
or any other network service, and it does not deploy, provision, enable, arm,
or upload a secret.

The command is disabled by default. Calling it without exactly one of
`--generate` or `--verify` creates nothing and fails. Both modes require an
explicit absolute `--private-root`; no default directory is selected.

## Generate or validate the bootstrap

### No additional recovery keys

The owner selected this operating path on September 21: reuse the existing
recovery signing key and RPC material; do not generate another recovery key or
require a GitHub App PEM to resume shipping. GitHub Actions supplies its existing
short-lived `GITHUB_TOKEN` to the fixed recovery gateway as a request credential.
The signer verifies signed GitHub OIDC identity before using that token to read
the fixed repository's source, checks and deployment evidence. The API token
does not authorize an operation by itself and is never stored in receipts,
Worker configuration or the recovery ledger.

The current source implements this path; hosted acceptance and deployment are
still required. A failed or expired job is resumed through an authenticated
workflow with a fresh token. An unresolved deployment stays pending until remote
readback proves its outcome. Existing App configuration remains compatible for
older installations, but obtaining a new App key is not a shipping prerequisite.

### Initial signer deployment

First complete the [prepared auth-bridge transition](auth-bridge-notification-prepared.md#prepared-transition-for-04)
and configure its authenticated observer. The named
`ReleaseRecoveryObservationEntrypoint` must exist before deploying the signer
that binds to it. Use the prepared transition to preserve existing production
authentication, secrets and Durable Objects. Do not upload the default bridge
configuration over the live service. The bridge transition does not require a
signer preparation receipt; signer deployment and gateway deployment follow it.

The initial private signer uses
`services/release-recovery/wrangler.preparation-signer.toml`. Its named entry
exposes the existing authenticated preparation and realm-observation methods
without importing final production fixtures. This breaks the dependency cycle
in which those observations are needed before the final fixtures can exist.
The gateway returns a sanitized 503 for final recovery methods in this phase;
the private signer's HTTP entry remains 404/no-store.

Keep recovery disabled. Before any upload, verify the account and live service,
ledger namespace, migration and authorization epoch. This configuration is for
initial provisioning only; do not use it to downgrade an existing full signer
or reset its epoch. Preparation still requires its exact policy, authenticated
workflow identity, transient GitHub API access, existing signing material and
bridge configuration. Successful bundling does
not establish those prerequisites or authorize a provider operation.

Promotion uses `wrangler.signer.toml`, with authenticated production fixtures
and the existing arming procedure. Both configurations preserve the same service,
named RPC entry and V2 ledger. For preserved G002/PTR state, use the authenticated
existing-state fixture path below; never fabricate old publication, atlas-import
or owner-provision receipts to satisfy the legacy input branch.

### Build fixtures from preserved realm updates

The fixture generator and toolchain bootstrap accept `--evidence=existing-state`.
This explicitly selects the fixed native reader for retained, authenticated
G002/PTR update completions. Omit it only for the original publication/import
receipt path. Missing or invalid adoption evidence fails; the producer never
switches to another evidence source automatically.

Use the pinned Windows Node from the [access guide](0.4.0-infra-access.md).
The operating Windows checkout and `/home/warpkeep/Warpkeep-0.4` must contain the
same integrated main and generated operation family. The fixed reader uses the
existing GitHub CLI account through private stdin when available. It reads actual
GitHub Verify/main evidence and the retained native records; no new login or
caller-selected receipt path is needed.

From that Windows repository root:

```powershell
$wkPrivateRoot = 'C:\Users\heyas\.warpkeep\private\release-recovery-v1'
& $wkNode services/release-recovery/scripts/prepare-release-recovery-wsl-toolchain.mjs --private-root $wkPrivateRoot --evidence=existing-state
& $wkNode services/release-recovery/scripts/generate-release-recovery-spacetime-fixtures.mjs --write --private-root $wkPrivateRoot --evidence=existing-state
& $wkNode services/release-recovery/scripts/generate-release-recovery-spacetime-fixtures.mjs --check --private-root $wkPrivateRoot --evidence=existing-state
```

Stop on a failed command and inspect its fixed caller before continuing. This
path does not need the legacy Windows canary, RPC or publication-record copies:
native adoption already authenticates the retained update. It verifies both
SHA-256 and Keccak of rebuilt programs, distinguishes full repository and module
trees, and reopens source evidence after building before publishing output.
The final fixture manifest stays at its existing format. These are local fixture
operations, not production deployments.

### Local bootstrap command

Use an owner-controlled private root outside every Git worktree and Desktop:

```powershell
node scripts/prepare-0.4.0-recovery-bootstrap.mjs `
  --generate `
  --private-root "$env:USERPROFILE\.warpkeep\private\release-recovery-v1"
```

The command rejects a filesystem, drive, or UNC share root, a
repository/worktree path or parent, the user-profile root or any of its
parents, the local or OneDrive Desktop (or a parent of either), and a path
containing a symbolic link or Windows junction. Do not use a build
output, CI workspace, artifact directory, shared sync folder, or Desktop.
On Windows it resolves the profile, Desktop known folder, and registered
OneDrive roots from the OS in addition to conservative environment-derived
paths, so changing `USERPROFILE` cannot remove those exclusions.

Generation creates or validates these fixed files:

- `recovery-bootstrap-marker.json`
- `recovery-signing-private.jwk.json`
- `recovery-signing-public.jwk.json`
- `recovery-signing-thumbprint.txt`
- `recovery-rpc-secret.txt`
- `recovery-census-pepper.txt`

The marker is exact canonical terminal-LF JSON in this key order:

```json
{"schemaVersion":1,"profile":"warpkeep-0.4.0-recovery-bootstrap-v1","keyId":"warpkeep-0.4.0-recovery-2026-09-03-1","enabled":false}
```

The RPC secret and census pepper are distinct canonical unpadded base64url
encodings of exactly 32 random bytes. They are also distinct from the decoded
P-256 signing scalar. Existing target files are never overwritten. A missing
target is created independently; every existing target must have its exact
canonical content and protection or the command fails closed.

The private root is mode `0700` and files are mode `0600` on POSIX. On Windows,
the command removes ACL inheritance and verifies one explicit full-control ACE
for the actual executing principal and exact equality between the object-owner
SID and the executing token SID. It does not trust `USERNAME` to identify that
principal. Secret files are opened exclusively, protected before bytes are
written, fsynced, and checked again. Revalidation descriptor-opens regular
non-link files and checks file identity before and after each bounded read.

Successful generation writes one safe line and nothing else:

```text
RECOVERY_BOOTSTRAP_READY generated <public-jwk-thumbprint>
```

The readiness word is `existing` when no target was created and `updated` when
only missing targets were added. The public JWK remains in its fixed file.
Neither output stream contains private JWK, RPC-secret, census-pepper, canary
FID, or component-commitment bytes. Errors contain only a stable
`RECOVERY_BOOTSTRAP_*` code.

## Supply the private canary FID and bridge public key

Generation never creates, requires, or selects either input in this section.
Before verification, the owner must separately provision these fixed files
under the same private root:

```text
player-canary-owner-fid.txt
auth-bridge-signing-public.jwk.json
```

The canary file's exact bytes are one canonical positive JavaScript-safe
decimal FID followed by a single LF. Do not pass the FID on the command line or
place it in Git, Desktop output, logs, shell history, or documentation.

The bridge public-key file is exact canonical terminal-LF JSON with ordered
keys `kty`, `crv`, `x`, `y`, fixed values `kty:"EC"` and `crv:"P-256"`, and
canonical 32-byte base64url coordinates. Provision it only from separately
authenticated, read-only auth-bridge JWKS/deployment readback. Never copy the
auth-bridge private signing JWK into this root. Both pre-existing files must
have the same owner-only protection as every private bootstrap file.

## Verify separation and compute the bridge identity

Run verification with the public deployment coordinates that will configure
the observer:

```powershell
node scripts/prepare-0.4.0-recovery-bootstrap.mjs `
  --verify `
  --private-root "$env:USERPROFILE\.warpkeep\private\release-recovery-v1" `
  --bridge-source-commit <lowerhex-40-source-commit> `
  --bridge-config-epoch <positive-safe-decimal> `
  --genesis-002-database <lowerhex-64-database-identity> `
  --ptr-database <lowerhex-64-database-identity>
```

Verification is read-only. It descriptor-reads only the fixed marker, key,
secret, canary, and bridge-public-key files. It derives the recovery signer's
public P-256 JWK and RFC 7638 thumbprint from the private JWK, validates the
stored recovery public files, validates the separate bridge public P-256 JWK,
and rejects bridge/recovery public-key or thumbprint equality. It also rejects
a decoded-byte collision among the recovery signing scalar, RPC secret, and
census pepper and requires the three realm database identities to be pairwise
distinct.

It then reproduces the auth bridge's exact 17-field canonical configuration
projection and length-framed SHA-256 identity. Fixed fields are semantic Worker
version `warpkeep-auth-bridge-release-recovery-v1`, Maincloud origin
`https://maincloud.spacetimedb.com`, audiences `warpkeep-spacetimedb`,
`warpkeep-genesis-002-spacetimedb`, and `warpkeep-ptr-spacetimedb`, and
`ptrEnabled:true`. The current Genesis 001 database identity is source-fixed.
The `signingPublicJwkThumbprint` projection member comes from the authenticated
auth-bridge public key, never from the distinct recovery-signer key. The canary
commitment uses the census pepper and the exact terminal-LF HMAC domain. The
Cloudflare Worker Version Metadata ID is deliberately not part of this
computed identity.

Only the final identity leaves the process:

```text
RECOVERY_BOOTSTRAP_VERIFIED <lowerhex-64-bridge-config-identity>
```

The bridge signing-key thumbprint, RPC digest, census-pepper digest, and
canary-FID HMAC are internal projection components and are not printed by
verification.
The marker's `enabled:false` is a containment assertion, not a deployment or
runtime control change. Keep `RECOVERY_ENABLED=false` until the separately
authorized arming and deployment procedure is complete.

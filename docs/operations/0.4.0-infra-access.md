# Warpkeep 0.4 infrastructure access

Maintained 2026-09-21. **Access guide and resumption procedure.**
Use alongside the release checklist and local-operations evidence. No credentials
belong in the release package. Reverify targets before every production operation.

## Hosting boundaries

- Frontend: GitHub Pages, https://warpkeep.com/.
- Auth bridge: Cloudflare Worker `warpkeep-auth-bridge`, https://auth.warpkeep.com/.
- Persistent realms: SpacetimeDB Maincloud; `warpkeep` (G001),
  `warpkeep-genesis-002` (sealed G002), `warpkeep-ptr` (isolated owner PTR).

Provider login is distinct from in-game owner authentication. Successful CLI
listing does not prove owner admission, possession of historical signing keys,
or that release-specific receipt and recovery requirements are satisfied.

## Resume without guessing

Start at the [execution handoff](../agent-notes/0.4.0/execution-handoff.md), then
inspect the actual [checkout role](0.4.0-development-sync.md#start-from-the-actual-checkout-and-remote),
live branch/PR and active process. Historical failure text is a lead to verify,
not a current blocker. Diagnose only the boundary needed for the next action.

| Boundary | Where to connect or inspect | Evidence needed before calling it blocked |
| --- | --- | --- |
| GitHub source and checks | Existing `gh`/Git access to `ael-dev3/Warpkeep`; the maintained checkout's actual remote | Live ref, PR head, exact run event/status and failing job/step. A pending run or a superseded cancellation is not failed authentication. |
| Native execution | Existing `WarpkeepRunner`, user `warpkeep`, and `warpkeep-wsl-production-01` Actions runner | Distinguish manual source checkout from Actions workspace, active process from stale journal, and offline runner from failed operation. Follow the [Linux guide](0.4.0-linux-runner.md). |
| Cloudflare provider | Existing `warpkeep-production` profile bound to the original checkout; commands below | Selected account plus the exact Worker operation. A successful deployment list proves read access only; wrong-default-profile results do not diagnose production access. |
| SpacetimeDB publisher | Owner's [ael-dev3 profile](https://spacetimedb.com/@ael-dev3); Windows CLI and the fixed Linux CLI config below | Compare `login show` with the owner profile, then list Maincloud and compare immutable realm identities to source. An empty list for another identity does not mean realms are absent. |
| G001 administrator observation | Fixed native census/policy operator and the protected environment's bridge admin secret | The operator obtains an application token from the Warpkeep auth bridge. A publisher CLI token has a different issuer: `INVALID_ISSUER` from a direct CLI admin procedure does not diagnose publisher login or the bridge secret. |
| Player/owner session | Existing Farcaster owner flow into isolated PTR through the auth bridge | Actual owner exchange/session and target admission. GitHub, provider login and an administrator token do not supply player identity. |
| Private release/recovery authority | Fixed private roots and guarded readers in the [Linux guide](0.4.0-linux-runner.md); existing recovery bootstrap in the [infrastructure audit](../agent-notes/0.4.0/release-and-infrastructure.md) | Identify the exact required receipt/key/binding and its authenticated producer. An empty sealed-state directory does not prove the recovery key is absent elsewhere. Inspect references/metadata without printing secret contents. |

For protected operations, use this order:

1. Verify the intended operation exists in the fixed workflow/caller and maps to
   the correct job. A missing implementation is agent work, not an owner login task.
2. Verify the selected main commit has a matching prepared family and completed,
   successful **push-to-main Verify**. Recheck main after waiting. Follow the
   [M1/M2 integration order](0.4.0-release-checklist.md#fixed-sequence); PR success
   alone and interim source-only M1 are insufficient.
3. Check only the credentials/private authority that this operation consumes.
   Preflight deliberately receives no provider secrets. Repository and
   environment variable/secret scopes differ; an empty environment list does not
   establish absence at repository scope. Secret names do not prove valid values.
4. Run the supported inspection once, capture its bounded result and exact failed
   stage, and use the owning reader/runbook to decide the next action. Distinguish
   source/toolchain refusal, provider denial, player denial and missing private
   evidence. Do not infer a precise cause from a generic `phase:"workflow"` alone.
5. After a repair, repeat the check that demonstrated the problem and update its
   canonical record. Preserve earlier evidence as dated history; stop presenting
   the old failure as current. Do not weaken a guard or invent evidence to pass it.

### Read the reported failure stage

The fixed Linux caller emits only a bounded failure code and phase. Use the
phase to narrow inspection; it does not prove a particular credential is missing.

Native G001 failures can also include a fixed `diagnostic` label. For example,
`g001-materialization` identifies the credential-free build, whereas
`g001-credential-descriptor` identifies opening the private credential after
authority refresh. Labels also distinguish host, source, closure, private roots,
prepared verification, observation, receipt and cleanup. They never include raw
exceptions, paths, provider responses or credential values. A label names the
failed stage; it does not prove a missing credential, rollback or lack of effects.

| Phase | Investigate first |
| --- | --- |
| `input` / `runtime` | Supported operation, matching job, runner/UID, environment and pinned executable. |
| `source` / `bundle` | Exact current main, clean authenticated bytes, compiler-input ancestry and complete generated family. |
| `workflow` | Construction of workflow authority: exact completed Verify, job evidence and required private inputs. Inspect the actual prerequisite; do not infer it from the phase alone. |
| `operation` | The selected operation function was entered. It may still be validating evidence or may have submitted work. Reconcile through that lane's existing private journal/continuation and supported readback before retrying. |
| `result` | The operation returned but its public result or subsequent attestation failed. Treat provider effects as unresolved until the supported reconciliation establishes them. |

Keep raw provider errors, credential material and private records private. A
sanitized failure is not proof of rollback, and a successful preflight is not
proof of deployment or mutation authority.

The protected Actions checkout is intentionally detached at the selected main
SHA. Native G001 readers use `attestPolicySource` to verify clean source bytes,
the matching `origin/main` commit and their operator. Do not route them through
the historical bootstrap checker that requires a local branch named `main`.
That mismatch rejects the checkout before a session or provider request exists.
Workflow duration alone does not establish that either census sample was taken:
materialization also takes time. Only authenticated retained census records and
the supported result establish observation progress.

## Ask the owner efficiently

Use existing session authorization and authenticated browser sessions first.
The agent handles routine inspection, source fixes, synchronization, CI diagnosis
and supported setup. The owner has authorized completing and shipping 0.4,
including repository writes, merges, required service configuration and deployment.
Continue those actions through the existing authenticated write paths; do not
ask for another general approval or treat an inspection command as the limit of
that authorization. Ask the owner only for an action that remains unavailable:

| Confirmed obstacle | Smallest useful human request | Agent's success check |
| --- | --- | --- |
| Correct account is known, but interactive login/MFA is required | “Please finish the open login for account X in tab Y.” Set up the real supported flow first. | Read back CLI identity, exact target listing and required local credential metadata. |
| Selected account differs and no verified owner session is available | “Which account owns these existing realms, or is that session on another device?” | Compare the selected identity and immutable targets after supported login. |
| A required historical private record cannot be found in the known roots | Name the missing record and ask which original machine/private location holds it; request a location, not its contents. | Authenticate the retained record through its existing guarded reader and check source/target binding. |
| Actual-owner or physical-device acceptance is ready | Give one short, prepared test, its URL, expected result and the specific observation needed. | Record the real result and distinguish it from fixture/emulation evidence. |

Each request should contain: the exact blocked action, what was checked, the
single missing human step and how the agent will verify it. Do not ask vaguely
for “all credentials,” ask for passwords/tokens/keys in chat, or repeatedly ask
for an action the owner already completed. Browser login alone does not update a
CLI session; complete its supported flow and confirm the readback.

If the response is pending, continue unrelated authorized work. If blocked work
must be handed off, record its owner and next action in the existing execution
handoff, without creating a new Desktop document or scheduling a new task.

## GitHub: source updates and release inspection

Use the existing authorized GitHub CLI/Git login for commits, pushes, protected
merges and workflow dispatch. The separate Warpkeep Release Recovery GitHub App
reads evidence for the deployed signer; its read permissions do not restrict the
agent's repository or deployment workflow. Do not replace working write access
with that App or request broader App permissions to repair an unrelated caller.

The following commands inspect release state without deploying:

```powershell
gh api repos/ael-dev3/Warpkeep/pages
gh pr list --repo ael-dev3/Warpkeep --state open
gh api repos/ael-dev3/Warpkeep/actions/runners
gh api 'repos/ael-dev3/Warpkeep/deployments?environment=github-pages&per_page=3'
```

For a returned deployment ID, read its `statuses_url`. Follow its actual Actions
run and artifact metadata to establish source and artifact provenance. An expired
artifact's recorded digest is not recoverable bytes or a usable rollback package.
Never treat local workflow emulation as GitHub Actions/OIDC identity.

## Cloudflare: select the production profile explicitly

The verified repo-local Wrangler version is 4.110.0, run with Node 22.22.3.
On the current Windows host, use the existing bound checkout and pinned executable
explicitly. A PATH `node` or a different working directory can select the wrong
runtime/profile. These are read-only commands:

```powershell
$wkNode = 'C:/Users/heyas/Documents/Codex/2026-08-11/pl/Warpkeep-0.4.0-worktree/.git/ci-node-22.22.3/node.exe'
$wkCloudflareCheckout = 'C:/Users/heyas/Documents/Codex/2026-08-11/pl/Warpkeep'
& $wkNode --version # Must report v22.22.3.
Push-Location -LiteralPath $wkCloudflareCheckout
try {
    & $wkNode services/auth-bridge/node_modules/wrangler/bin/wrangler.js --version
    & $wkNode services/auth-bridge/node_modules/wrangler/bin/wrangler.js auth list
    & $wkNode services/auth-bridge/node_modules/wrangler/bin/wrangler.js deployments list --profile warpkeep-production --name warpkeep-auth-bridge --json
    if ($LASTEXITCODE -ne 0) { throw 'Inspect the exact Cloudflare read failure.' }
} finally { Pop-Location }
```

Confirm the Node executable/version before these commands. Do not run package
installation against the current shared dependency junction. Setup in a fresh
isolated checkout must use the repository's pinned dependency/toolchain process.

Production account: `c647739b4535010b0b13e6fc296e2c4e`. The default profile in the
0.4 worktree currently selects another account and must not be used implicitly.
The existing `warpkeep-production` profile is bound to the original `Warpkeep`
checkout; it can be selected explicitly for supported operational commands.
In Wrangler 4.110.0, `whoami --profile` is unsupported. To inspect its identity,
run `whoami --json` in the already bound checkout, or use `--cwd` with that
checkout's actual path. Do not switch global profiles just to run a check.

Profile storage is under `%APPDATA%/xdg.config/.wrangler/config/`, with encrypted
credential material protected by Windows Credential Manager. Reference this
location; never copy profile files, export tokens or include logs in the package.
If authentication fails, use the supported login/profile reauthentication flow
with the owner. Do not extract keys or substitute an unrelated account.

Public discovery is available at
https://auth.warpkeep.com/.well-known/openid-configuration and public keys at
https://auth.warpkeep.com/.well-known/jwks.json. These expose public metadata,
not private signing keys, player records or proof of owner login.

## SpacetimeDB: identities and schema inspection

The verified Windows executable is
`%LOCALAPPDATA%/Programs/SpacetimeDB/2.6.1/spacetime.exe`. Check the actual
installation rather than assuming a historical alternate CLI path exists.

```powershell
$warpkeepSpacetime = Join-Path $env:LOCALAPPDATA 'Programs/SpacetimeDB/2.6.1/spacetime.exe'
& $warpkeepSpacetime --version
& $warpkeepSpacetime login show
& $warpkeepSpacetime server ping maincloud
& $warpkeepSpacetime list --server maincloud --yes
& $warpkeepSpacetime describe --server maincloud --no-config --yes --json warpkeep-ptr
```

Inspect the production Linux login separately; the Windows session does not
automatically synchronize credentials into WSL:

```powershell
$wkLinuxCli = '/home/warpkeep/.warpkeep/release-preparation-v1/toolchain/spacetime-2.6.1/spacetimedb-cli'
$wkLinuxConfig = '/home/warpkeep/.warpkeep/private/production-admin-v1/spacetime-cli.toml'
wsl.exe -d WarpkeepRunner -u warpkeep -- $wkLinuxCli --config-path $wkLinuxConfig login show
wsl.exe -d WarpkeepRunner -u warpkeep -- $wkLinuxCli --config-path $wkLinuxConfig list --server maincloud --yes
wsl.exe -d WarpkeepRunner -u warpkeep -- /usr/bin/stat -c '%F %h %u:%g %a' $wkLinuxConfig
```

The native config must be a nonsymlink regular file, single link, owner
`1000:1000`, mode `600`, with its parent private directory mode `700`. Check these
through the existing guarded caller as well; metadata does not establish provider
permission. The expected realm constants live in the
[existing-update adapter](../../scripts/ptr-production-existing-update-adapter.mjs)
and [G001 policy reader](../../scripts/genesis001-policy-observation-receipt.mjs).

Never add `--token` to `login show`. The listing and schema commands are marked
unstable by this CLI, so preserve the version with verification records.
Compare listed immutable identities to the release ledger before selecting a
database. Database names alone are not an adequate deployment target check.

For a future mismatch, compare `login show` with the actual owner profile before
changing credentials. The supported `login --no-browser` flow clears the selected

owner's browser session. Keep login URLs and credential bytes out of Git. Recheck

Linux, use the existing production config and restore its required `0600` mode
after login; see [the runner guide](0.4.0-linux-runner.md#existing-ptr-module-updates).

The verified schema read does not export rows. Player-data access and baseline
capture must use the approved authenticated operations and private evidence
store. Do not paste row exports, FIDs, raw receipts or configuration files into
public documentation or the workspace delivery package. If a row query returns
permission denied, stop that operation; successful schema/list access is not permission to
bypass row access restrictions.

## Mutation and recovery boundary

This guide intentionally supplies no standalone publish/reset commands. Use the
reviewed release operation entrypoints and exact frozen artifacts only after the
mandatory baseline, source, receipt, review and recovery checks pass.

Never reset or recreate G001. Freeze only new admissions while preserving existing
players and legitimate timers. Keep G002 sealed. Test the real owner journey in
PTR; do not open admissions to make a test pass. Recovery must preserve writes
made after deployment, not restore an old database snapshot over active state.

The final package must include the verified release-specific setup, deployment
and recovery entrypoints and their results. This access guide alone does not
satisfy those delivery requirements.

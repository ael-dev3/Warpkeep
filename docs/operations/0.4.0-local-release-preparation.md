# Prepare a complete local release source

The current local source selects the dedicated WSL distro `WarpkeepRunner`,
account `warpkeep` (required UID/GID 1000), and `/home/warpkeep`. This is the
observed guest setup: Ubuntu 24.04.4 boots and runs commands as `warpkeep`
UID/GID 1000. The home is mode 0750 and private build directories are 0700.
Pinned native preparation and independent checking passed for recorded source
`03cb8b8fc2c0c59bcb58c4303b2082dead6325d9`, producing candidate
`release-workspace-2d70e1808817fcf50990e5a4b84409b9`. That evidence does not cover
later gameplay/workflow edits or an uncommitted worktree. Re-attest the guest,
fixed tools and private roots through the existing checks before a new run.
There is no fallback to another project's distro or home. The dedicated Actions
runner also uses account `warpkeep`, UID/GID 1000; its job authority and separate
private recovery state are verified independently of local preparation.

Existing tool/OS/kernel digest pins remain fail-closed. Bootstrap and attest the
new guest through the existing owners; preserve prior cache/receipt history,
and do not rewrite old attestations or prepared handles with the new paths.
Preserve the completed native candidate as source-bound evidence. Prepare and
independently check a new committed input when changed runtime or workflow source
needs release validation; do not relabel the old candidate as current.
From Windows, explicitly enter `wsl.exe --distribution WarpkeepRunner --user warpkeep`
before using the Linux commands below.

The operating entry is `scripts/local-release-assembler.mjs`. It compiles the
committed source, installs one complete generated family into a separate Linux
candidate, verifies every candidate byte and retains a recoverable journal.
It produces source for review; it does not deploy, authorize a release, change
admissions or obtain player credentials. Its `finalReleasePrepared` field is
always `false`; release acceptance is established separately.

See the [release engineering evidence](../evidence/0.4.0/release-engineering.md)
for executed results and limitations. A component test, a diagnostic compiler
probe or an `installed-unverified` transaction is not a completed assembler run.

## Execution environment

Use the owner's native WSL Linux filesystem and an independent checkout of the
exact committed preparation source. The current supported profile is Linux x64,
UID 1000, ext4, with the private root
`/home/warpkeep/.warpkeep/release-preparation-v1`. Its `runs`, `cache` and
`toolchain` directories are owner-only. The operating Node is the attested
22.22.3 executable at the fixed path shown below. The compiler runtimes also
verify their installed tools and locked package archives.

The Windows worktree is the editable source. Its shared `node_modules` junction
is not an installation destination. The operating checkout must contain the
committed preparation modules at their exact Git bytes; uncommitted runtime
edits and hidden index changes are rejected. No ordinary dependency installation
is needed in that checkout.

The closure scanner uses TypeScript 7.0.2 and its Linux native package from the
auth-bridge lock. Its exact archive inventory is generated by
`scripts/local-prepared-closure-scanner-manifest.mjs`. The runtime authenticates
the fixed private cache and installs or reattests the owner-only namespace. It
maps only the closure policy's fixed TypeScript imports; it does not resolve
through the checkout's service `node_modules` directory. Do not hand-edit the
manifest or copy a convenient installed package tree into authority.

## Prepare and inspect

Before creating another run, follow the
[output and retention rules](../engineering/development-workflow.md#output-locations-and-retention).
Check Windows host and WSL guest free space, inspect existing run sizes and the
actual process state, and reuse the fixed tools/cache. Do not rerun preparation
for an ordinary documentation edit or create Desktop copies of candidates.
Keep the handle and evidence needed for continuation in the existing notes.

From the independent committed Linux checkout, use a clean environment:

```bash
env -i HOME=/home/warpkeep PATH=/usr/bin:/bin LANG=C.UTF-8 LC_ALL=C.UTF-8 TZ=UTC \
  /home/warpkeep/.warpkeep/release-preparation-v1/toolchain/node-v22.22.3-linux-x64/bin/node \
  scripts/local-release-assembler.mjs prepare
```

The command prints bounded phase records, including the draft and final
`release-workspace-<hex>` handles, and a final JSON result only on success.
Retain the final handle. The reported `candidateRoot` contains the reviewable
source checkout. Its Git HEAD still identifies the input source; generated
changes are intentionally not committed by the assembler.

The fixed producers check G001 compilation, binding stability and compatibility;
derive complete G002/PTR bindings; build and load the operation bundles; and
build the recovery workflow bundle. The assembler then derives source pins,
the reachable deployment inventory, its manifest and generated consumers from
that same source. It rejects compiler inputs that disagree with installed
candidate bytes. All other tracked files, including preserved G001 files, must
remain byte-identical to the committed source.

Only the temporary derivation draft is rolled back. A successful final candidate
keeps its journal and owner-private `prepared-source.json` result outside the
checkout. That result records source, family, journal and scanner digests. It
does not supply production evidence or make a manually edited candidate valid.

## Check an existing candidate

Replace the example handle with the exact final handle printed by `prepare`:

```bash
env -i HOME=/home/warpkeep PATH=/usr/bin:/bin LANG=C.UTF-8 LC_ALL=C.UTF-8 TZ=UTC \
  /home/warpkeep/.warpkeep/release-preparation-v1/toolchain/node-v22.22.3-linux-x64/bin/node \
  scripts/local-release-assembler.mjs check release-workspace-<hex>
```

Use the same committed operating source as the candidate. `check` holds the
candidate lock, recompiles from a fresh captured source, independently derives
the expected generated consumers and compares the full candidate and journal.
It does not derive expected non-pin bytes from the candidate being checked.
Repeated verification must converge to identical generated bytes. An interrupted
valid completion may finish its marker; a rolled-back or edited candidate fails.

## Recover an interrupted or unwanted candidate

```bash
env -i HOME=/home/warpkeep PATH=/usr/bin:/bin LANG=C.UTF-8 LC_ALL=C.UTF-8 TZ=UTC \
  /home/warpkeep/.warpkeep/release-preparation-v1/toolchain/node-v22.22.3-linux-x64/bin/node \
  scripts/local-release-assembler.mjs recover release-workspace-<hex>
```

Recovery restores the journal's exact prior bytes under the same candidate
lock. It preserves unexpected user changes by refusing to overwrite them.
Completion or pending metadata moves to `prepared-source.history.json` only
after rollback. Restarted recovery re-establishes file and directory durability
before reporting success; the historical marker never labels a recovered
candidate as currently prepared.

A failure may leave private workspaces and diagnostics. Follow the actual
process handle before retrying; elapsed time or a journal alone does not prove
that a compiler stopped. Preserve an unrecognized or pre-journal interruption
for inspection. Do not delete shared tools, change ownership, reset the editable
worktree or invent a completion marker to get past a failed check.

Recovery is rollback, not disk cleanup. It retains candidate history. There is
no automatic age-based pruning policy for these authoritative runs: inspect
references, process state and recovery needs before retiring anything. Clean
only proven disposable compiler/test output through its owning cleanup path;
do not delete `runs/`, `cache/` or `toolchain/` wholesale.

## Integrate the reviewed source

Export only after `prepare` and the independent `check` return exactly the same
profile, handle, candidate root, source commit and tree, transaction, journal,
family, closure and scanner digests, verification counts and
`finalReleasePrepared: false`. Reacquire the candidate lock with
`acquirePreparedReleaseCandidateLock`. Use `readLocalBindingBoundedFile` and
`decodePreparedReleaseJournal` to authenticate the canonical
`prepared-source.json`, its recorded identity, the sole transaction journal,
the candidate device and inode, and the absence of rollback state. Require every
retained backup to match its journal fact and every current output to match the
recorded mode, size, digest, device and inode. Recompute the sorted complete
family count and digest, then call `verifyPreparedReleaseCandidateBytes` with
the retained source, candidate, exact source commit and tree, and captured
output bodies while the lock remains active.

The reviewed operator can create the Git patch in the verified candidate; it
does not need another clone or copied worktree files. Snapshot the normal Git
index by identity and digest, create an exclusively named temporary index under
the candidate's `.git`, and populate it from the exact input tree. Hash each
captured output body with `git hash-object -w --no-filters --stdin`; require the
returned object ID to equal the independently computed Git blob ID. Feed exact
mode `100644`, object ID and validated path records to `git update-index` through
NUL-delimited `--index-info`. Do not reread output paths through Git filters.

Write the staged tree and compare it with the exact input tree. Its raw,
no-rename diff must contain only the output paths whose captured bytes differ
from the input, with the expected modes and object IDs; outputs already equal to
the input remain members of the authenticated family even though the patch omits
them. Emit only `git diff --cached --binary --full-index --no-ext-diff
--no-textconv` from that temporary index. Before accepting the patch, reattest
the lock, source and candidate identities, full candidate bytes, completion
marker, journal, backups, outputs, rollback absence and the untouched normal
index. Remove the owned temporary index; loose content-addressed objects are not
release authority and must not be deleted speculatively.

On the existing clean checkout at the actual input commit M1, first authenticate
the patch digest and metadata and recheck its exact HEAD, tree, full status and
normal index. Run `git apply --binary --check` and only then plain
`git apply --binary`; do not use reject, three-way, cached or index modes. After
application, require HEAD and the normal index to be byte-identical to their
pre-apply state, the changed-path set to equal the patch metadata, every output
to have its recorded bytes and digest, and every non-output path to remain at
M1. A rejection must leave both the index and worktree unchanged. Generated
manifests continue to identify M1 as their committed compiler input; do not
rewrite those source IDs to the later generated-only commit.

The retained 8033 candidate exercised this composition without a new clone or
copied files: all 3,199 source and candidate files and 102 outputs verified; the
seven changed paths produced an 8,368-byte patch with SHA-256
`08b9df9eb47f8ee5847245608d7877960e128023beb6a7ecaf86c942c0f4198a`
and staged tree `dd15feb7e229de09dd911236526baadf7be41c9f`. An isolated-index
`git apply --cached --check` and `git apply --cached` reproduced that tree, while
the source, candidate, normal index and control records remained unchanged and
the temporary index was removed. This retained evidence does not cover a fresh
M1; prepare and independently check that committed input before its export.

Run affected verification, scan the outgoing source range, publish a reviewed
development commit and compare the GitHub ref as described in
[source synchronization](0.4.0-development-sync.md). Final preparation must be
repeated after remaining gameplay or deployment inputs change. Actual supported
runner identity, authenticated provider observations, live owner play, recovery
and release acceptance remain required before shipping.

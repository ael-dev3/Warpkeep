# 0.4.0 live delivery

The owner authorized completing and deploying 0.4.0 on 2026-09-04, including
necessary changes to the release architecture. Earlier instructions in planning
documents limiting work to local preparation or requiring the unavailable old
Mac are superseded for this delivery. Existing production data, authenticated
identity checks, and accurate deployment evidence still must be preserved.

- GitHub: the configured `gh` login has administrator/push access to
  `ael-dev3/Warpkeep`. The frontend uses **GitHub Pages**, with custom domain
  `warpkeep.com`; it is not a Cloudflare Pages project.

  Its immutable identity agrees with the auth bridge configuration. Genesis 002

  their names does not expose their values. Preserve managed bindings when
  uploading a new Worker version; do not recover secrets into source or logs.

The initial access checks were authenticated read observations. Two new private
database modules have since been deployed. The complete 0.4.0 release, auth
bridge changes, PTR owner provisioning, and frontend activation are not shipped.

### Delivery scope after the product assessment

Treat the assessment as product direction, not an authenticated playtest. The
0.4 delivery priority is the existing sealed realm split, reliable entry and
reconnection, and clear gathering/construction decisions. Preserve Genesis 001
at 0.3 with its existing players; do not open Genesis 002 or admit a test cohort.
PTR remains a separate, explicitly provisioned admin-only realm.

The construction clarity changes above are the bounded player-facing work for
this release. New production bonuses, shortened construction timers, and
additional building mechanics need a separate PTR experiment before promotion;
they are not prerequisites for shipping the sealed release. Do not expand this
release into a renderer/provider rewrite. Extract modules only when needed to
fix a concrete release defect behind existing tested interfaces.

Physical-device acceptance remains outstanding: authenticated entry, dispatch,
reconnect, background/resume, and repeated scene switching need device evidence.
Construction can be exercised only where it is actually enabled. Record load
time, frame pacing, memory growth, and failures on named devices; synthetic
browser fixtures and passing source tests must not be reported as phone proof.

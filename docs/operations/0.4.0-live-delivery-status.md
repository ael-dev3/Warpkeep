# 0.4.0 live delivery

The owner authorized completing and deploying 0.4.0 on 2026-09-04, including
necessary changes to the release architecture. Earlier instructions in planning
documents limiting work to local preparation or requiring the unavailable old
Mac are superseded for this delivery. Existing production data, authenticated
identity checks, and accurate deployment evidence still must be preserved.

## Verified access

- GitHub: the configured `gh` login has administrator/push access to
  `ael-dev3/Warpkeep`. The frontend uses **GitHub Pages**, with custom domain
  `warpkeep.com`; it is not a Cloudflare Pages project.
- Cloudflare: the configured Cloudflare connector can access the active
  `warpkeep.com` zone and `warpkeep-auth-bridge`, including its settings and
  deployment history. Its `auth.warpkeep.com` custom domain is attached to that
  Worker. The local Wrangler login currently selects a different account;
  an empty list there does not show that the production Worker is missing.
- SpacetimeDB: the configured 2.6.1 CLI lists the existing `warpkeep` database.
  Its immutable identity agrees with the auth bridge configuration. Genesis 002
  and PTR are absent from the associated database listing.
- Worker signing, session, admin, and RPC secrets are still configured. Reading
  their names does not expose their values. Preserve managed bindings when
  uploading a new Worker version; do not recover secrets into source or logs.

These are authenticated read observations, not a claim that a deployment has
completed. No 0.4.0 production version has been deployed by this work.

2. Repair the release source inventory and its generated consumers. It contains
   obsolete paths and excludes source required by the approved PTR design.
3. Complete or replace unfinished recovery execution. In particular, the
   fixture host's WSL bootstrap and execution functions still deliberately fail;
   synthetic unit tests do not prove they are operational.
4. Build and test an executable release path using current authenticated
   accounts. Preserve Genesis 001, create distinct G002/PTR databases, verify
   their actual state, and preserve existing managed Worker secrets.
5. Publish reviewed source through the repository's checks and deploy the
   matching Worker/frontend. Verify live identity, version, auth, and realm
   behavior; record rollback versions and only then label 0.4.0 shipped.

Historical receipts cannot be reconstructed as though an old operation had
occurred. A replacement authorization flow must use fresh evidence and clearly
identify itself as a new recovery operation.

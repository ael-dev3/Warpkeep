## Status and maintenance

From PowerShell, inspect only selected unit fields and sanitized GitHub metadata:

```powershell
$wkRunnerUnit = 'actions.runner.ael-dev3-Warpkeep.warpkeep-wsl-production-01.service'
wsl.exe -d Ubuntu-24.04 -u root -- systemctl show $wkRunnerUnit --property=ActiveState,SubState,UnitFileState,User,Group,MainPID,Result
gh api repos/ael-dev3/Warpkeep/actions/runners --jq '.runners[] | {name,labels:[.labels[].name],status,busy}'
```

An active service can briefly precede GitHub reporting the runner online. Inspect
both states before restarting it. Avoid publishing raw journal or diagnostic
output; inspect failures privately and report only the relevant sanitized cause.

Start an intentionally stopped, healthy installation with:

```powershell
wsl.exe -d Ubuntu-24.04 -u root -- systemctl start $wkRunnerUnit
```

Before stopping for maintenance, confirm the exact runner is idle and no recovery
job or unresolved deployment is using it. If a job is busy or its outcome is
uncertain, inspect that run and its reconciliation state first. Do not delete
receipts, clear locks, replace registration or kill an unrelated process.

```powershell
wsl.exe -d Ubuntu-24.04 -u root -- systemctl stop $wkRunnerUnit
```

The unit is enabled for future distro starts; installation required no WSL
restart. It does not keep Windows awake or ensure WSL launches after Windows
boots. Availability depends on the Windows host, network and running distro.
No Windows startup task or sleep setting was changed. The existing failed
`getty@tty1.service` was unrelated and left untouched.

## What this enables, and what remains

The recovery production job matching this profile is
[`deploy-pages.yml` → `deploy-recovery`](../../.github/workflows/deploy-pages.yml).
The signer independently checks the real job's name, labels and group through
[GitHub evidence validation](../../services/release-recovery/src/githubOidc.ts).
The sealed-realm workflow now has a dedicated Linux **preflight-only** caller,
described below. Legacy durable Pages and notification production lanes still
target macOS/ARM64. Sealed publish, import, owner and activation operations refuse
before checkout until their own supported callers are complete.

A real recovery run still requires:

1. The complete generated source/bundle family installed in the reviewed source,
   plus an authenticated schema 2 recovery activation binding. The current
   [canonical recovery-candidate reader](../../scripts/sealed-realms-production-recovery-candidate.mjs)
   derives authenticated Git/bootstrap/corpus facts and supports completed
   historical inspection. Genuine recovery, Worker, module and approval producers
   remain incomplete. A prepared directory or fixture JSON cannot replace those
   facts and the genuine receipt chain.
2. The actual recovery gateway/private signer, keys, durable ledger, observer
   binding and release-specific authorization state. Checked-in
   [signer configuration](../../services/release-recovery/wrangler.signer.toml)
   remains disabled. Creating the private directory grants no authorization;
   the workflow obtains and persists its verified claim for the exact run.
3. Successful `Verify` for a push of the selected current protected `main`,
   classification into `sealed-g002-recovery`, exact artifact attestation,
   fresh claim and deployment-boundary checks, then mandatory live postflight.
   GitHub CLI/browser login is neither job OIDC identity nor Cloudflare authority.

## Supported sealed preflight

[`sealed-realms-production.yml`](../../.github/workflows/sealed-realms-production.yml)
retains manual dispatch, protected current `main`, job `operate`, environment
`notification-bridge-prepared`, read-only GitHub permissions and the shared
non-cancelling production lock. Select only `preflight` with that exact source
commit after its prepared family and required main Verify evidence are valid.
The other operations fail explicitly; they cannot trigger a provider mutation.

The workflow verifies the real installed account and roots, clean committed
bootstrap files, fixed Git executable, and exact Node 22.22.3 Linux/X64 bytes.
It stages Node under the runner's private temporary directory, rejects ambient
runtime overrides and passes the GitHub token only through the inherited
environment. No dependency installation occurs. The
[fixed caller](../../scripts/sealed-realms-production-linux-preflight.mjs) then
authenticates prepared ancestry, the complete selected G001 source graph,
bundle/declaration and actual attested import before invoking the existing G001
factory and operation. It reopens source and runtime identity around both awaits.

`preflight-inspected` establishes source, workflow and private-root inspection.
It does not establish provider readiness, signer authorization, player acceptance
or launch readiness. A failure reports only a bounded phase; retain actual job
identity and inspect the relevant canonical checks rather than overriding a hash,
path, account, source or factory to force progress. Git or Node upgrades require
a reviewed runtime-policy change with matching verification.

The sealed roots were absent at the first September 8 inspection. They were
created separately as UID/GID 1001 using checked directory descriptors, no-follow
opens, mode `0700` and directory fsync. Every ancestor under the account home
was validated, with no access/default ACL; all three final roots were empty.
No credentials, receipts, keys or authorization records were created, and no
existing root was repaired. Runtime preflight continues to validate existing
roots only; it never provisions them. The account's `nologin` shell is intentional:
maintenance uses a direct `runuser -u runner -- <fixed executable>` invocation
from the administrator context, rather than enabling an interactive account.

Native tests execute the real bundled caller under UID/GID 1001 in a private mount
namespace with synthetic read-only GitHub responses. Workflow tests exercise its
actual shell guards and source/token transport. These establish local composition,
not a successful protected dispatch. See dated
[engineering evidence](../evidence/0.4.0/release-engineering.md) for the exact source
and test scope. A new combined source must undergo its own native preparation and
independent check before operating.

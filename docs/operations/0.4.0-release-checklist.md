## Fixed sequence

Representative playable keep → required gameplay/visual coverage and local
operations → final release freeze → deployment → live verification → workspace
handoff. Do not freeze while gameplay or deployment source is unfinished.
Use the Astra keep, gameplay and assembler specifications as the current design
baseline. The owner's current goal authorizes improving mechanics, architecture,
and weak implementations when it benefits the game or delivery. Record the reason
and update affected specifications and evidence; preserve the real release
conditions below. Complete the requested GitHub/documentation refresh first.

The historical M1 candidate
`release-workspace-83bf0da57a1a622d84742c445f8450a9` was prepared and independently
checked from signed `27c2d276`; its generated-only M2 was promoted through
`810286c95f39cf6e41f121162fa5dab250a77a16` and passed main Verify and read-only
preflight. These results remain bound to those sources.

For a new operation-bundle source change, preserve the repository's squash-only
integration and compiler-input ancestry:

1. Publish the reviewed source repair and derive its deployment closure from
   canonical Git blobs. Pass the required checks and merge this source-only M1.
2. Verify the actual signed M1 merge and reviewed tree. Prepare and independently
   check the complete generated family from that exact clean **main commit**.
3. Integrate that authenticated family in a generated-only M2 through normal
   protections. Preserve its M1 source identity; do not relabel a development
   candidate whose input is absent from main ancestry after squash.
4. Wait for M2's exact push-to-main Verify to succeed, recheck live main, and then
   run preflight. Do not dispatch protected operations against interim M1, where
   the operation bundles still describe the previous source graph.

The historical M2 completed this sequence: source-only M1 `645637e1`,
generated-only PR #274, successful main Verify/CodeQL, native checkout fast
forward and exact-source preflight. Do not dispatch a provider mutation until
the operation-specific private producer is present and its supported
read-only inspection succeeds.

Development preparation can validate a repair before integration, but cannot
replace the source-bound M1 preparation/check or M2 acceptance.
